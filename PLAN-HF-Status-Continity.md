# Локальная визуализация TTM HF-эпиков: файл, Jira-доска и отдельный эпик

Обновлено: 23.09.2026. Статус: план v2 дополнен анализом одного эпика по Jira-ссылке (S9), импортом по одним ключам и отображением первоначального Открыто вне расчёта TTM (S10). Решения Q1–Q3 сохранены с расширением числа режимов до трёх. Реализация и доступ к Jira в рамках этой правки не проверялись.

Подробная реализация: [технический план](TECH-PLAN-HF-Jira.md) — три источника, модель v3, локальные API, алгоритмы, миграция и проверки. Фактический ход реализации и результаты приёмки вынесены в [отчёт](IMPLEMENTATION-HF-STATUS.md); исходные требования ниже не заменяются результатами разработки.

Основания и найденные расхождения: [проверка требований в три прохода](REVIEW-HF-Business-Requirements.md). Обозначения S0–S8 ниже отсылают к сообщениям пользователя и исходному плану в этом отчёте. Техническое предложение не считается подтверждённым бизнес-требованием; описание уже существующей функции само по себе не подтверждает её обязательность в v2.

S9 — пользовательская история от 23.09.2026: «Для анализа конкретного эпика, в роли пользователя хочу дать его джира-ссылку, и получить ту же визуализацию по этому эпику». Она добавляет третий источник выборки к S8; остальные согласованные правила продолжают действовать.

S10 — уточнения пользователя от 23.09.2026 по результатам проверки плана: «Нам нужен по идее только ключ. Остальное можно получить с помощью API» и «Давай тоже будем отображать статус Открыто, но в расчёте не применяется». Второе уточнение относится к первоначальному Открыто, в том числе к эпику, ещё не вошедшему в активный этап; согласованное правило возвратов `↩О` внутри TTM сохраняется.

## Результат

Уточнение S12 при реализации от 23.09.2026: пользователь подтвердил, что на доске 1482 завершённые задачи не скрываются. Это параметр проверенной доски, а не правило для всех Jira-досок.

Уточнение S11 при реализации от 23.09.2026: для статуса «Решили делать», обнаруженного в Jira перед первым активным HF-этапом, пользователь выбрал «Вне TTM: учитывать работу с первого согласованного активного HF-этапа». Этот начальный период не делает границу TTM неизвестной и не входит в расчёт. Уточнение относится к периоду до начала TTM; непрерывность уже начавшегося TTM сохраняется.

Три режима: ссылка на Jira-доску, загрузка файла CSV/XLSX или Jira-ссылка на конкретный эпик. Доска, файл либо ссылка на эпик задаёт кандидатов; приложение оставляет актуальные HF по данным Jira и исключает отклонённые эпики. Во всех режимах оно получает полную историю из Jira и показывает таблицу длительностей с heatmap слева и календарную последовательность этапов справа. Для ссылки на эпик результат относится к одной указанной задаче.

Для файлового режима достаточно ключей эпиков; остальные необходимые данные приложение получает через API Jira. Первоначальное Открыто отображается на календаре, но его время не входит в расчёт TTM. Эпик, ещё не начавший работу, также виден в визуализации.

Приложение работает на Mac пользователя. Локальный Node-сервер читает PAT из macOS Keychain и обращается к Jira от имени владельца токена. Интерфейс и сервер слушают только `127.0.0.1`, приложение не публикуется в интернете. Для свежих данных нужна доступность корпоративной Jira; сохранённый результат открывается без сети.

Jira остаётся источником истории во всех режимах: для файла и доски — по S6, для отдельного эпика — в рамках той же визуализации по S9. Форматы CSV/XLSX подтверждены S8; отдельный пользовательский режим без Jira в объём v2 не включён. Просмотр ранее сохранённого кэша остаётся унаследованной возможностью. В рамках составления и проверки плана Jira и Keychain не читаются, права и настройки Codex не меняются: требование к будущему приложению не является разрешением ассистенту на живую проверку.

## Прямо подтверждённые решения новой постановки

- Три независимых источника выборки: файл, доска или ссылка на отдельный эпик. Файл и доска согласованы в S6/S8; отдельный эпик добавлен в S9. Jira даёт историю для выбранных эпиков во всех режимах.
- По Jira-ссылке на конкретный эпик пользователь получает ту же визуализацию для этого эпика; для такого анализа не требуются файл или ссылка на доску (S9).
- Файловый режим принимает CSV и XLSX. Отклонённые эпики исключаются; принадлежность к HF определяется текущими данными Jira (S8).
- Единственные обязательные данные файла — распознаваемые ключи эпиков. Название, тип, резолюция, статусы, даты и история получаются через API Jira; их наличие в файле не требуется (S10).
- Первоначальное Открыто показывается, но исключается из расчёта TTM, сумм этапов и heatmap. Последующее Открыто внутри TTM остаётся возвратом `↩О` и учитывается по прежнему правилу (S10, S0).
- Для доски брать все HF-эпики, которые показывает сама доска с её постоянными настройками, без временных быстрых фильтров (S5). Родительские эпики любых задач не были выбраны как отдельный источник.
- Контрольная ссылка (S4): https://hq.tutu.ru/secure/RapidBoard.jspa?rapidView=1482&projectKey=HOTELS
- Приложение работает только на локальной машине пользователя и обращается к Jira с PAT из Связки ключей (S3).
- Для выбранных эпиков нужна «такая же визуализация» (S3, S9); её исходные правила перечислены ниже.

## Унаследованные требования исходного плана

Основание — S0: пользователь поручил реализовать исходный план. Перечисленные ниже требования сохраняются с уточнением отображения первоначального Открыто из S10.

- Только HF; DF и отклонённые исключаются. Исключение отклонённых подтверждено и для доски ответом Q1 (S8).
- Jira используется только для чтения. PAT остаётся в локальном помощнике, не передаётся в браузер, файлы, логи или кэш. Приложение слушает `127.0.0.1` и не публикуется в интернете.
- Полная история статусов и impediment; отсутствующая история не подменяется агрегатами Excel. Частичные ошибки показываются у соответствующих эпиков.
- Нормализованные данные и история сохраняются в `.local-data/` вне Git. При запуске открывается последний кэш с временем обновления; старые и свежие данные различаются.
- Правила TTM приведены в отдельном разделе ниже. Пороги heatmap берутся из исходной процедуры и не меняются попутно.
- Слева: ключ, название, TTM, «Возврат в открыто», суммы активных HF-этапов и heatmap. Справа: кварталы, месяцы и дни, цветные сегменты с кодами `П`, `В`, `С`, `ПР`, `ГР`, `Р`, `Э`, `ОР`, `↩О`, финиш `🏁` и отдельная штриховка impediment. Узкие сегменты не растягиваются ради подписи.
- Согласно S10 календарь также показывает первоначальное «Открыто» с явным отличием от рассчитываемого интервала TTM и от возврата `↩О`. Диапазон календаря охватывает и этот начальный период.
- Сортировка по умолчанию — TTM по убыванию; поиск по ключу/названию, сортировка, закрепление заголовков и левой области, горизонтальная прокрутка, масштаб «День / Неделя / Месяц», диапазон по всей выборке.
- Точные дата, время и длительность — в подсказках; панель эпика содержит метаданные, переходы, предупреждения, время синхронизации и ссылку Jira. Исходные визуальные ориентиры — `Jira Upgrade НТ.pdf` и `image.png`; их новая трактовка в этом аудите не вводилась.
- Сборка, модульные и локальные интеграционные тесты; автоматизированное браузерное визуальное тестирование — только по отдельной просьбе.

## Границы первой версии

- В выборку входят HF-эпики до начала работы, активные и закрытые, если их показывает доска с постоянными настройками; скрытые ею закрытые эпики автоматически не добавляются.
- В режиме отдельного эпика выборка определяется его ссылкой и не зависит от присутствия на какой-либо доске. Допускается эпик до начала работы, активный или закрытый по тем же правилам HF и резолюции.
- DF и отклонённые исключаются во всех режимах по актуальным данным Jira. Причины исключения видны, в том числе при прямой ссылке на исключённый эпик.
- Ручное обновление без фонового опроса — техническое предложение первой реализации, не отдельное требование пользователя.
- Временные быстрые фильтры, поиск в открытой вкладке и её несохранённые настройки не воспроизводятся. Приложение не читает cookies или профиль браузера.
- Точное действие постоянных фильтров, подфильтров, колонок и скрытия завершённых задач доски 1482 нужно проверить через доступный API и контрольную выборку.
- Если для воспроизведения доски нужен контекст вне её постоянных настроек, сначала установить ограничение и задать пользователю конкретный вопрос. Выбор спринта как новая функция приложения заранее не согласован.
- Автоматизированное браузерное визуальное тестирование остаётся вне объёма без отдельной просьбы.

## Пользовательский сценарий

Сценарий конкретизирует S0, S3, S5, S6, S8, S9 и S10. Поведение refresh и открытия кэша — проектная детализация этих требований.

1. Выбрать источник: «Файл», «Доска Jira» или «Эпик Jira».
2. Для доски или эпика вставить соответствующую Jira-ссылку; для файла — загрузить CSV или XLSX, в котором достаточно ключей эпиков. Приложение проверяет источник.
3. Получить выборку и показать её происхождение: имя доски, файла либо ключ и ссылку отдельного эпика, правила отбора, число найденных и исключённых эпиков.
4. Получить историю выбранных эпиков из Jira. Показать прогресс и ошибки отдельных задач. Предыдущий набор остаётся видимым до публикации нового результата. Кнопка отмены — отдельное предложение, не подтверждённая часть сценария.
5. Построить визуализацию, включая первоначальное Открыто вне расчёта TTM. Если эпик ещё не вошёл в активный этап, показать его Открыто и пояснение, что TTM ещё не начат. Показать источник, момент среза, время загрузки и полноту данных.
6. «Обновить» для доски заново получает её состав и историю. Ушедшие эпики исчезают из новой выборки, появившиеся добавляются. Для файла сохраняется исходный набор кандидатов; новые задачи вне этого набора берутся только из нового файла. Переименование ключа той же задачи не считается добавлением нового кандидата. Для всех сохранённых кандидатов заново проверяются HF и резолюция по Jira: отображаемый состав может измениться, включая повторное включение ранее исключённой задачи. Для отдельного эпика обновляются признаки и история той же задачи.
7. Повторный запуск открывает последний кэш. Само открытие кэша не вызывает Jira и не сдвигает момент среза.
8. При ошибке доступа показать её; не переключаться на автономный импорт и не выдавать агрегаты за успешно загруженную Jira-историю.

## Получение выборки доски

Техническое предложение для выполнения S5. Конкретный API и его соответствие постоянной видимости пока не проверены.

- Определять состав через поддерживаемый API Jira, не через разбор HTML.
- Поддержать предоставленный формат RapidBoard URL с `rapidView`; другие форматы добавлять после проверки их однозначного разбора.
- Из ссылки извлекать id доски; 1482 — контрольный пример. Не добавлять `project = HOTELS` только из-за параметра `projectKey`: самостоятельное ограничение проектом пользователь не задавал.
- Учитывать постоянный фильтр доски, подфильтр, отображаемые статусы и правила скрытия завершённых задач. Не считать заранее, что один API-метод автоматически повторяет все эти условия.
- Получать все страницы и устранять повторяющиеся ключи. Первую страницу или первые N задач не считать полной доской.
- Отделять Jira issue type, бизнес-вид эпика и тип потока HF/DF. Поле/признак HF и допустимые значения проверить на конкретной Jira. Не считать любой Epic или «Большую задачу» HF автоматически.
- Исключать отклонённые эпики, даже если они видны на доске (Q1). Неизвестные или противоречивые признаки показывать как проблему отбора.
- Права владельца PAT ограничивают доступную выборку. Не обещать полноту относительно задач, которых этот пользователь не видит.
- Если API не позволяет воспроизвести постоянные настройки доски, показать ограничение, не подменяя выборку всеми эпиками проекта.
- Для приёмки сравнить набор ключей с вручную подтверждённой выборкой доски 1482 под тем же пользователем, без быстрых фильтров.

## Получение выборки файла

- Сохранить поддержку обеих XLSX-выгрузок (S0, S2) и добавить CSV Jira (S8).
- Минимально достаточный CSV/XLSX содержит только ключи эпиков — остальные колонки не обязательны. Отсутствие названия, HF/DF, резолюции, статуса, дат, TTM или истории в файле не является ошибкой импорта при наличии распознаваемых ключей (S10).
- Недостающие сведения для отбора и визуализации получить через API Jira. Дополнительные колонки файла могут служить контрольными данными, но не являются условием загрузки.
- Читать текущие признаки Jira для всех корректных ключей файла, не отбрасывая их заранее по устаревшим HF/DF или резолюции. По Jira оставить HF и исключить отклонённые. Сохранить всех кандидатов для повторного отбора при refresh.
- Полная история отобранных эпиков берётся из Jira (S6). Раздельное хранение исходных и текущих метаданных — техническое предложение для объяснения расхождений.
- Если метаданные файла устарели, явно показывать расхождение с Jira; не смешивать их без указания источника.
- CSV/XLSX со снимком полей задаёт кандидатов, но не становится историей переходов. Предоставленные агрегаты остаются контрольными значениями файла.

## Анализ отдельного эпика по ссылке

Основание — пользовательская история S9. Режим использует уже согласованные правила данных и визуализации.

- Пользователь передаёт Jira-ссылку на один конкретный эпик. Она задаёт единственного кандидата для анализа.
- Приложение получает актуальные сведения из Jira и проверяет, что задача является HF-эпиком и не отклонена. Для неподходящей задачи показывается причина исключения; для неверной или недоступной ссылки — ошибка получения данных.
- Для подходящего эпика загружается полная история статусов и impediment. Правила полноты, предупреждений, TTM и расчётного среза совпадают с остальными режимами.
- Отображаются та же таблица длительностей с heatmap, календарная последовательность этапов, первоначальное Открыто вне расчёта TTM, возвраты, повторные этапы, отдельный impediment и панель деталей — для одного эпика. Отсутствие первого активного этапа не исключает эпик из отображения.
- Ссылка на доску и табличная выгрузка для этого сценария не нужны. Обновление и сохранение результата используют общие правила приложения.

## Полная история и карта статусов

Требование полной истории и сохранения неизвестных статусов унаследовано из S0. Проверки API, пагинации и транспорта ниже — предлагаемые способы его выполнения.

- После фиксации ключей читать метаданные, историю статусов и изменения поля impediment только для выбранных эпиков.
- Проверить способ получения полной истории в установленной версии Jira. Наличие `expand=changelog` не доказывает полноту. Конкретные endpoint и схему пагинации закрепить после диагностики.
- Проверять полноту страниц, дубликаты, порядок событий и согласованность истории с исходным и текущим состоянием задачи.
- Если доступна только обрезанная история, отмечать эпик как неполный и не выдавать календарь за точный. Агрегаты файла остаются отдельным источником.
- Поле impediment определять по метаданным Jira, не зашивать случайный номер custom field. Недоступное поле или его история означают неизвестную длительность, не ноль.
- Неизвестные HF-этапы, например «Проверка идей», не переименовывать в старые этапы и не применять чужие пороги heatmap. Если рабочие статусы отличаются, согласовать явную карту начальных, активных и конечных статусов.
- Ограничить параллелизм; предусмотреть таймауты, прекращение запросов и ограниченные повторы временных ошибок. Пользовательская кнопка отмены не является условием реализации этих механизмов.

## Правила TTM и согласованность

Основание — S0, сохранение визуализации в S3/S9 и уточнение первоначального Открыто в S10. Обработка неоднозначных данных конкретизирует запрет выдумывать переходы; алгоритмы согласования среза ниже отмечены как технические предложения.

- Начало TTM — первый вход в активный HF-статус по согласованной карте. Дата создания не подставляется вместо неизвестного начала.
- Первоначальное Открыто до первого активного этапа отображается по подтверждённым границам истории Jira. Его время исключается из TTM, сумм этапов и heatmap и не относится к показателю «Возврат в открыто». Последующее Открыто внутри TTM сохраняется как `↩О` и входит в TTM, включая незавершённый возврат.
- Если полная история подтверждает, что эпик ещё не входил в активный этап и остаётся в Открыто, показывать его начальный интервал Открыто до `asOf` и пояснение «TTM ещё не начат». TTM не рассчитывается и не подменяется нулём; такой эпик не помечается как находящийся в работе. Неполная история сама по себе не доказывает отсутствие активного этапа.
- Конец начавшегося TTM — последний переход в окончательный Закрыт. Для эпика, вошедшего в активный этап и остающегося незакрытым, конец TTM — единый `asOf`; последний сегмент TTM отображается стрелкой и признаком «В работе».
- Повторные входы остаются отдельными сегментами. Промежуточное закрытие при переоткрытии сохраняется.
- Неизвестные и смешанные статусы внутри определённого TTM сохраняют время и выделяются штриховкой. Неизвестный статус перед первым известным активным этапом не отбрасывается молча: начало TTM может быть неопределённым.
- Использовать точные timestamps и отображать Europe/Moscow. Сумма непрерывных сегментов внутри границ TTM равна TTM без округления по дням. Отображаемое первоначальное Открыто находится вне этих границ и в эту сумму не входит.
- Impediment показывать отдельно, не вычитать автоматически. TTM из файла с вычитанием impediment остаётся отдельным контрольным показателем.
- Техническое предложение: фиксировать общий `asOf` в начале синхронизации. Пользователь не выбирал начало вместо конца задания отдельно. Переходы после среза не удлиняют расчёт; более поздние метаданные не считаются одновременными этому срезу.
- Чтение доски и задач не является гарантированной атомарной транзакцией. Сохранять время начала/окончания загрузки и состав выборки. При обнаружении изменения страниц или конфигурации доски повторить чтение в пределах лимита либо отметить несогласованность.
- Если выборка доски неполна, не заменять предыдущий полный набор под видом успешного обновления. Если ключи получены полностью, а история отдельных эпиков недоступна, допустим частичный набор с причинами.
- Старую историю не подмешивать незаметно в новый срез. При неудаче оставлять прежний набор с прежним временем и сообщением об ошибке.

## PAT и локальность

Локальность, Keychain, защита секрета и чтение Jira — S0, S3. Конкретные механизмы и записи Keychain ниже являются техническими предложениями; актуального разрешения на живую диагностику нет.

- Браузер обращается только к локальному серверу; PAT не попадает в браузер, localStorage, URL и ответы API.
- PAT читать через системный механизм Keychain с аргументами процесса без shell-подстановок. Локальная инструкция `use-atlassian-mcp` указывает `Code Jira Relations PAT` и альтернативную `tutu-jira`; наличие и пригодность ещё не проверены. В диагностике явно перечислить используемые записи.
- PAT не писать в кэш, файлы, логи, ошибки или тестовые снимки. Не сохранять долговременно вне Keychain.
- Разрешить клиенту только `https://hq.tutu.ru`. Не передавать авторизацию на другой хост или по перенаправлению. Произвольные адреса из введённой ссылки не запрашивать.
- Сохранить проверки Host/Origin, локальные POST-заголовки и CSP. К Jira обращается только Node-сервер.
- Jira-операции — только чтение; список реально используемых API закрепить после диагностики.
- Перед первой живой диагностикой подготовить проверяемый список конкретных запросов и записей Keychain. Запросить узкое разрешение с выбором разового/сессионного или постоянного срока. В рамках текущего планирования такое чтение не выполняется.
- Постоянные правила доступа не создавать без явного выбора пользователя и отдельного разрешения на защищённые файлы. Если потребуется изменение harness, выполнить действующие правила его зеркалирования. Работа самого приложения не должна зависеть от изменения Codex harness.

## Предлагаемые изменения в коде

Это проектные решения для трёх подтверждённых режимов. Контракт нового источника «эпик по ссылке» необходимо конкретизировать при синхронизации технического плана. Автономные контракты и данные прежней версии сохраняются только в рамках технической совместимости и чтения старого кэша; нового пользовательского режима без Jira они не добавляют. Пользовательская отмена во всех строках и API ниже — дополнительное предложение вне подтверждённого объёма, а не обязательная функция.

| Область | Планируемое изменение |
| --- | --- |
| `shared/types.ts` | Общий тип источника: файл, доска или отдельный эпик по ссылке; правила отбора, время среза и полнота. Нормализованную историю отделить от имени `TableHistory`, сохранив совместимость. |
| Новый модуль Jira на сервере | Получение PAT, клиент с ограничением origin, адаптер версии Jira, выборка и полная история. Зависимости подменяются тестовыми реализациями. |
| `server/service.ts` | Загрузки и обновления всех трёх источников, стадии прогресса, отмена, частичные ошибки, публикация согласованного результата. |
| `server/import.ts` | Существующие XLSX и новый CSV Jira как кандидаты для проверки HF/резолюции и загрузки истории из Jira; прежний автономный контракт изолирован как совместимость. |
| `server/timeline.ts` | Переиспользовать расчёт; проверить первоначальное состояние и события по обе стороны `asOf`. |
| `server/cache.ts` | Новая схема и миграция текущего набора; нормализованные входные данные и происхождение, без токена. |
| `server/app.ts` | Локальные операции загрузки доски, отдельного эпика по ссылке, импорта с историей, обновления и отмены; сохранение имеющихся контрактов автономного импорта. |
| `src/App.tsx` | Выбор источника, ссылка, правила отбора, прогресс, ошибки подключения, время среза и обновление; существующая визуализация сохраняется. |

Предлагаемые локальные операции: `POST /api/board/import`, `POST /api/refresh`, `POST /api/jobs/:id/cancel`; существующие `GET /api/dataset`, `GET /api/jobs/:id`, `POST /api/import` сохраняются. Операция загрузки отдельного эпика по ссылке уточняется в техническом плане. Для файла режим чтения Jira передаётся явно, без неявного сетевого запроса по старому автономному контракту. Формат тела и ошибок закрепляется перед реализацией API.

## Последовательность реализации

1. Использовать зафиксированные ответы Q1–Q3 и дополнения S9/S10: исключение отклонённых, отбор по Jira, три режима, достаточность ключей в файле и первоначальное Открыто на календаре вне расчёта TTM. Позже синхронизировать технический план согласно указанию пользователя. Подготовить контрольные сценарии доски 1482 и отдельного эпика.
2. Подготовить ограниченную диагностику и получить разрешение на запуск. Проверить вариант/версию Jira, видимость доски для PAT, поля HF/impediment и полноту истории на минимальном наборе задач. Секреты не выводить.
3. Реализовать общий контракт источников, миграцию кэша и адаптер Jira с тестовыми ответами, включая пагинацию и ошибки.

6. Выполнить модульные и локальные интеграционные проверки, сборку, затем разрешённую живую приёмку. Обновить README по реализованным возможностям.

## Критерии проверки требований

Методы проверки предложены технически; новые функции не становятся согласованными от включения в этот список.

- Состав HF-эпиков совпадает с контрольной выборкой доски 1482 без быстрых фильтров после исключения отклонённых. Проверены скрытые/закрытые эпики, DF и отклонённые задачи.
- Файл, доска и ссылка на эпик задают независимых кандидатов; Jira определяет HF, резолюцию и даёт историю. Отбор файла и его refresh следуют одинаковым правилам текущей Jira. Старые DF/отклонённые в файле не теряются до проверки Jira.
- CSV и XLSX только с ключами успешно задают кандидатов; отсутствие остальных полей не вызывает ошибку структуры. При одинаковых ключах и срезе состав и расчёт по Jira совпадают с результатом расширенного файла с дополнительными колонками.
- По корректной ссылке на доступный неотклонённый HF-эпик показывается ровно этот эпик с той же визуализацией. Файл и доска для загрузки не требуются. При одинаковом срезе результат совпадает с отображением того же эпика в выборке из файла или доски.
- Для прямой ссылки проверены исключение DF/отклонённого эпика с причиной, неверная или недоступная ссылка, неполная история и обновление той же задачи.
- Проверены несколько страниц доски и истории, дубликаты, изменение настроек и состава между обновлениями. Неполная выборка не объявляется полной.
- На контрольных эпиках повторные статусы и точные даты совпадают с историей Jira. Сумма сегментов внутри границ TTM равна TTM с точностью исходных timestamps; первоначальное Открыто отображается отдельно от этой суммы.
- Во всех трёх режимах эпик с подтверждённой полной историей только в первоначальном Открыто виден на календаре, его TTM ещё не начат. Для маршрута `Открыто → active → Открыто → active` начальное Открыто видно, но не входит в расчёт; возврат `↩О` входит в TTM и показатель возврата.
- Проверены неизвестные статусы, несколько переходов одновременно, закрытие/переоткрытие и короткий impediment.
- Недоступный/истёкший PAT, запрет Keychain, отсутствие VPN/сети, 401/403/404, временные ошибки и лимиты дают понятное сообщение; предыдущий пригодный набор сохраняется.
- Частичная история не подменяется старой историей или агрегатами. Дата открытия кэша не выдаётся за свежий срез Jira.
- PAT отсутствует в браузерных данных, API, логах и кэше. Неподдерживаемая ссылка/перенаправление не получает токен.
- Поддерживаются полная XLSX-выгрузка, недельный XLSX и CSV Jira. В интерфейсе три режима: доска, файл и отдельный эпик по ссылке; все используют историю Jira.
- Проходят сборка, модульные и локальные интеграционные тесты. Живая приёмка выполняется в пределах отдельного разрешения.

## Что ещё нужно подтвердить

Бизнес-решения Q1–Q3 внесены в оба плана; дополнения S9/S10 пока внесены только в этот бизнес-план. Их перенос в технический план отложен по указанию пользователя. Архитектура предложена, но до разрешённой диагностики нельзя утверждать, что PAT доступен приложению, владелец токена видит нужную доску или отдельный эпик, постоянные настройки доски полностью воспроизводимы через доступный API, а история статусов и impediment получается без обрезки. Новая карта статусов при необходимости требует отдельного содержательного решения. Эти пункты — следующие шаги, а не уже полученный результат.
