# Проектирование: раскрытие связанных элементов

## Базовая версия и подтверждения

Единственный репозиторий — `.`, ветка `main`, HEAD `9962dac112a70ce05b9656b4cf4f792b91bb2720`. Исходники приложения и SDD ещё не отслеживаются Git, поэтому HEAD не является полной исходной версией изменения. [Сверка](implementation-review.md) и [протокол](verification.md) фиксируют проверенное рабочее дерево и контрольный прогон. Перед реализацией следует повторно проверить состояние и сохранить относящиеся к изменению исходные файлы; несвязанные изменения не перезаписывать.

## Текущий и целевой потоки

Сейчас `DatasetService` получает только исходные HF-эпики, собирает истории и атомарно сохраняет набор. Автономный парсер истории отбрасывает ключи вне исходной HF-выборки; интерфейс не позволяет выбрать автономный режим.

Целевой путь Jira: исходные кандидаты → прежний отбор HF → направленный граф связей → метаданные и доказанные истории уникальных достижимых элементов → общий срез и производные полосы → атомарная запись → локальное раскрытие.

Целевой автономный путь: явно выбранный режим книги → основной лист и дополнение → проверки типов, связей и историй → та же модель графа и полос → запись → локальное раскрытие. Формат описан в [контракте книги](xlsx-format.md).

Загрузить граф и истории при импорте/обновлении; нажатие стрелки работает по сохранённому набору. Это позволяет восстанавливать дерево без Jira и держать один срез. Получение данных по каждому нажатию отвергнуто для этого изменения: оно потребовало бы отдельной публикации состояния и смешивало бы моменты наблюдения.

## Модель и существующий владелец данных

Владельцем остаётся `DatasetService`, запись проходит только через `CacheStore`. Отдельная база данных не требуется. Добавить `shared/hierarchy.ts` с типами нормализованного графа и представления связанных элементов, `server/hierarchy-schema.ts` с проверками сохраняемых входов.

Дополнение `hierarchy` в `JiraInputs` и `ImportedSelection` содержит версию расширения 1, момент среза, узлы по устойчивой идентичности, направленные рёбра, привязку исходных эпиков к узлам, состояние состава каждой ветки, исходные истории/метаданные, основания определения конечного закрытия и предупреждения. Для Jira идентичность — `issueId`, ключ является изменяемым атрибутом; для автономной книги — нормализованный ключ в пределах набора. Рёбра хранят исходное отношение, не только дерево отображения.

Производное `dataset.hierarchy` содержит рассчитанные интервалы и нормализованный граф. Исходные `dataset.epics`, аудит корневого отбора и расчёт статистики не пополняются дочерними узлами. На один Jira-объект по устойчивому ID создаётся общий процесс получения снимка; его результат используется исходной и дочерней проекциями. Число родителей не создаёт дополнительных процессов. Контрольные запросы и один повтор при нестабильности входят в этот же процесс. Флаги не определяют качество дочерней полосы.

В автономном наборе явный срез дополнения должен сохраняться в `dataset.asOf`, даже когда у корней есть только агрегаты. Миграция и выбор календаря не должны проверять наличие истории исключительно у корней. Если же явного среза нет, дочерние интервалы не считаются доказанными.

## Jira: связи, типы, закрытие

Расширить `JiraIssue` и адаптер для `issuelinks`, `issuetype.subtask`, стабильного идентификатора статуса и его категории. Метаданные необязательного дополнения проверять отдельно: повреждённые связи не должны стирать уже доказанный исходный эпик. Отсутствующее поле связей означает неизвестный состав явных связей. Пустая ветка подтверждается только при пустом массиве issuelinks и доказанно пустом стандартном составе Epic Link.

Для каждого локального представления связи сопоставить `outwardIssue` с `type.outward`, `inwardIssue` с `type.inward`. Подпись `contains` даёт ребро текущий → связанный, `is contained in` — связанный → текущий. Обходить только рёбра, где текущий узел — содержащий родитель. Использовать проверенную пару подписей типа связи, нормализуя регистр и пробелы; не определять смысл только по словам inward/outward. Иные типы игнорировать. Циклы и повторные рёбра обрабатывать отдельно.

Для FR-031 / AC-048 по уточнению пользователя от 29.09.2026 адаптер при чтении каждого эпика дополнительно вызывает `GET /rest/agile/1.0/epic/{id}/issue` вне контекста доски. Это стандартный состав Epic Link, показанный в Jira как «Задачи, составляющие бизнес задачу», а не дополнительное имя типа issuelinks. Параметры: `startAt`, `maxResults=100`, `fields=key`, `jql=ORDER BY key ASC`; фильтров состояния, резолюции, проекта или исполнителя нет. Пагинация использует существующий `collectPages`: неизменный total, точный startAt, уникальные ID, отсутствие пустой промежуточной страницы; предел 10 000 элементов и 200 страниц. Основание — [REST Jira Software Server 9.12.4](https://docs.atlassian.com/jira-software/REST/9.12.4/); это подтверждение контракта соседней версии, живая проверка 9.12.10 фиксируется отдельно.

Состав Epic Link и contains объединяется по паре стабильных ID родитель/ребёнок. Граф, общий процесс чтения истории и кэш остаются прежними. Каждое контрольное чтение эпика заново читает его стандартный состав, поэтому подпись связей обнаруживает изменение членства даже при прежнем updated. Задачи и подзадачи стандартный состав не запрашивают. Сбой 403/404, ошибка схемы, нестабильная/усечённая пагинация сохраняют contains и дают `EPIC_MEMBERSHIP_UNAVAILABLE`, `linksKnown=false`; неподтверждённые страницы Epic Link не публикуются как полный состав. Глобальные ошибки авторизации, сети, отмены и частоты продолжают прерывать весь импорт. После обновления кода старый сохранённый набор надо обновить из Jira; одно обновление страницы не читает новые связи.

Для автономного XLSX формат не меняется: состав Epic Link заранее представляется строками «Связи» как `эпик contains задача`; обращения к Jira нет.

Получать `statusCategory` через метаданные статуса или `GET /rest/api/2/status` один раз на запуск. Использовать категорию статуса на срезе по его ID, а не категорию текущего статуса, если после среза были переходы. Сохранять исходное значение, способ определения закрытия и версию правил вместе с историей; восстановление кэша не обращается в сеть.

Приоритет правил закрытия, согласованный по ответу пользователя:

1. Распознанная категория Jira — основной источник. `done` и документированный вариант `completed` означают закрытие; `new`, `indeterminate` и `in-flight` — незакрытое состояние. `undefined`, отсутствие и незнакомые значения не дают ответа по категории. Не определять категорию по цвету, локализованному имени или числовому ID.
2. Если категории нет или она не распознана, для эпика статус `[HF] Закрыт` либо `[DF] Закрыт` означает закрытие. Другие статусы с распознанным префиксом соответствующего потока не закрывают эпик. Тип «эпик» проверяется по метаданным, а не только по префиксу. Для эпика без распознанного потока и категории результат неизвестен.
3. Для обычной задачи без пригодной категории использовать название статуса по словарю ниже. Незнакомое название даёт неизвестный результат, а не автоматически «открыто» или «закрыто». Резолюция определяет исключение отклонённых элементов, но не дату закрытия.

Согласованный словарь реализации для задач использует полное совпадение после нормализации регистра, пробелов и `ё/е`. Закрывающие названия: «Закрыт», «Закрыто», «Закрыта», «Готово», «Выполнен», «Выполнено», «Выполнена», «Завершён», «Завершено», «Завершена», «Решён», «Решено», «Решена», `Closed`, `Done`, `Completed`, `Resolved`. Незакрывающие: «Открыт», «Открыто», «Открыта», «Новый», «Новая», «Новое», «В работе», «В процессе», «Переоткрыт», «Переоткрыто», «Переоткрыта», `Open`, `New`, `To Do`, `In Progress`, `Reopened`. Подстроки не используются: «Не закрыто» и «Готово к тестированию» не считаются закрытием. Этот конечный словарь — техническая конкретизация разрешённой пользователем логики названий, а не сведения о фактических статусах всех команд.

При определении по названию сохранять и показывать основание «по названию статуса». Отсутствующая категория не блокирует полосу, если резервное правило дало ответ. Нераспознанная категория дополнительно даёт предупреждение. При противоречии известной категории и названия категория имеет приоритет, расхождение отмечается. Если ни одно правило не дало ответа, только соответствующая полоса остаётся неизвестной. Эти правила одинаковы для Jira и автономного XLSX, где категория может быть передана в книге, а сетевой запрос отсутствует.

Основные ключи категорий приведены в [документации Atlassian для Server](https://developer.atlassian.com/server/jira/platform/jira-issue-statuses-as-lozenges/); примеры REST 9.12.2 ниже также используют `completed`/`in-flight`. Это основания поддерживаемых вариантов, не результат проверки целевой Jira. Заключительная живая приёмка T012 сверяет наблюдаемые данные; неизвестные значения уже имеют определённую обработку.

Официальная [документация Jira 9.12.2](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.2/) описывает статусы с категориями и признак подзадачи. [Модель связей Atlassian](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/) объясняет сопоставление стороны и подписи. Это основание дизайна; примеры Cloud и соседней версии Server не доказывают ответы установленной Jira 9.12.10. Живая проверка является отдельной обязательной задачей приёмки.

Новый `server/jira/hierarchy.ts` использует общую очередь с пределом четырёх одновременно выполняемых чтений. Нельзя запустить отдельные пулы по четыре на каждую ветку. Для объектов сохраняется прежняя проверка `updated` после чтения и одна повторная попытка; сравнивать также подпись связей/метаданных, а не полагаться только на `updated`. Повторный снимок не объединять с прежним; при нестабильности отметить состав/историю частичными. Атомарного снимка всей Jira нет.

## Отбор и обход

Исходный фильтр `decideEligibility` применяется только к корням. Для потомков: явная подзадача исключается без обхода; обычная задача является листом; любой эпик, включая DF, обходит дочерние связи. Отклоняющая резолюция проверяется общей нормализацией `isRejected`: «Отклонено», «Отклонён», `Rejected`, а после живой сверки также «Не будет выполняться». Последний вариант одинаково применяется к корням FR-005 и потомкам FR-030; AC-003 и остальные правила отбора сохраняются. Проверка идёт по резолюции; пустая известная резолюция допустима. Неизвестность типа или резолюции не подменяется предположением — показывается диагностическое состояние.

Отклонённый эпик не получает строку. Его неотклонённые потомки сохраняются через ближайшего видимого предка с пояснением; исходные рёбра сохраняются для объяснения пути. Общие узлы используют общий процесс получения снимка, но отображаются под каждым родителем. Набор посещённых узлов ограничивает получение данных; набор предков текущего пути предотвращает циклы в отображении. Эти два набора не взаимозаменяемы. Одинаковый ребёнок у одного видимого родителя после свёртки отклонённых промежуточных узлов отображается один раз. Для пояснения достаточно одного подтверждённого пути через скрытые узлы; все исходные рёбра остаются в графе, но перечислять и сохранять все комбинации маршрутов не требуется.

При раскрытии видимого родителя обход скрытых отклонённых эпиков выполняется итеративно, с отдельным набором посещённых скрытых узлов для этого родителя и текущего набора видимых предков. Каждый скрытый узел раскрывает свои исходящие рёбра не более одного раза в таком обходе. Достижение допустимого узла завершает продвижение по этой ветке до следующего действия раскрытия. Повторы допустимого ребёнка объединяются, возврат к предку даёт предупреждение о цикле. Для пояснения хранить ссылки на предшественников и восстанавливать один маршрут по запросу; не материализовать все маршруты. Повтор скрытого узла сам по себе не считается циклом: цикл определяется по состоянию обхода/предкам, а общие потомки — допустимые повторы. Эти ограничения действуют и когда вся скрытая ветка не имеет ни одного допустимого потомка.

## Расчёт дочерней полосы

Новый `server/related-timeline.ts` принимает метаданные, доказательство полноты и упорядоченные переходы/интервалы. Проверка непрерывности может использовать выделенные общие функции, но HF-расчёт и `statusInfo` не становятся фильтром входных статусов.

Сначала сравнить создание со срезом: если элемент создан позже среза, сохранить его как диагностическую строку «Создан после среза» без интервалов и маркера закрытия. Такое состояние не является ошибкой полноты истории; оно отражает то, что граф получен при загрузке, а календарь относится к более раннему срезу. Нельзя создавать отрицательный интервал или включать дату будущего создания в календарный диапазон. Создание ровно на срезе допускает нулевую границу, но не положительную длительность. Затем применить срез к переходам, сохранив известное состояние на этот момент. Начало — создание. Если конечное состояние закрыто, конец — последний переход в конечный закрывающий статус; если нет переходов и элемент закрыт с создания, показать только нулевую границу. Если не закрыто, конец — срез. Промежуточные закрытия и любые повторения остаются сегментами; статусы после среза не отображаются. Интервалы полуоткрытые, их сумма равна длине показанной полосы. Конечный закрывающий статус представлен маркером. Не доказаны создание, цепочка или конечное закрытие — точной полосы нет; пригодность исходного родителя не теряется.

Палитра дочерних полос детерминирована идентичностью статуса; доступные названия не заменяются общим знаком «?». Для коротких сегментов переиспользуется `segmentLabels`; даты и исходное имя сохраняются в подсказках. Геометрия использует миллисекунды и существующие масштабы 26/8/3 пикселя в сутки.

## Интерфейс

Новые `src/HierarchyRows.tsx` и `src/RelatedStatusBar.tsx` выводят дочерние строки; `shared/hierarchy-view.ts` строит пути отображения. ID состояния раскрытия включает исходный эпик и весь путь. Кнопка имеет `aria-expanded`, понятную подпись и отдельный фокус. Нажатие не открывает панель исходного эпика. При сворачивании скрываются потомки; сохранённое раскрытие вложенных веток сбрасывается, чтобы повторное открытие снова показывало один уровень.

При новом наборе и перезагрузке страницы всё свёрнуто. Масштаб/сортировка и временное скрытие корня фильтром не сбрасывают раскрытие текущего набора. Поиск и исполнитель продолжают фильтровать исходные эпики, дети показываются вместе с выбранным родителем; это поясняется у фильтров. Дети упорядочены по ключу внутри родителя.

В режиме «Состав из Excel» дочерних полос нет, сохранённое раскрытие возвращается при переходе к календарю. Автономный набор с доказанными дочерними интервалами должен позволять календарь, даже если у корневого эпика нет числового TTM. Общий диапазон вычисляется по исходным и доказанным интервалам допустимых дочерних элементов всего набора, а не только раскрытым строкам или прошедшим фильтр корням. Исключённые отклонённые узлы, подзадачи, недостижимые узлы и диагностические строки без интервалов не участвуют; допустимые потомки скрытого отклонённого эпика участвуют. Отбор допустимых дочерних элементов для диапазона не зависит от текущего состояния раскрытия.

Подтверждённо пустой эпик не имеет активной стрелки. Для незагруженного старого набора указано «Данные о связях не загружены» и доступное действие обновления Jira либо повторного импорта книги. Неизвестный состав ветки даёт предупреждение. Задача без истории остаётся диагностической строкой без метрик.

## Хранение, совместимость и откат

Сохранить внешнюю оболочку кэша v3 и профили `jira-v3` / `legacy-v2`; добавить необязательное версионированное дополнение `hierarchy` со строгой схемой. Его отсутствие в старом кэше — «не загружено», неизвестная версия — ошибка совместимости с сохранением исходного файла. Включить дополнение в обе схемы кэша, оба пути построения набора и миграцию v2 → v3. Непроверенные производные интервалы с диска не принимать за источник.

Публиковать дополнение в той же атомарной записи, что и корни. Ошибка сериализации/записи не меняет текущий набор. Refresh строит новый граф с нуля; истории прежнего графа не подмешиваются.

Перед вводом реализации сохранить локальную резервную копию исходных файлов и сырого кэша с прежними правами доступа, вне Git и Google Drive. Старое приложение сможет прочесть оболочку v3, но не покажет дополнение и при новом сохранении может его потерять. Поэтому откат — восстановление исходных файлов и резервного кэша при остановленном сервере, а не запуск старой версии поверх единственной копии новых данных. Испытать этот порядок на временном кэше.

## Ошибки, пределы и наблюдаемость

| Событие | Результат |
| --- | --- |
| 403/404 объекта, частичная/противоречивая история | Диагностическая строка или неизвестная ветка; пригодные соседи доступны |
| Глобальные 401, отмена, остановка по 429, смена версии | Остановка запуска чтений; прежний набор сохраняется |
| Книга без дополнения | Прежние данные плюс состояние незагруженной иерархии |
| Противоречивые метаданные/версия книги | Ошибка нового импорта, прежний набор остаётся |
| Цикл | Один диагностический конец ветки, без бесконечного обхода |
| Ошибка записи | Прежний набор и граф целиком остаются |

Защитные пределы: 10 000 уникальных узлов вместе с корнями, 50 000 уникальных рёбер; существующий предел 1000 исходных HF остаётся. При превышении сохраняется явная неполнота, а не молчаливое усечение. Это согласованные технические пределы; граф сверх них остаётся явно неполным. Если реальные входы требуют большего объёма, задача полного показа остаётся открытой до изменения решения.

Выводить строки порциями до 200 путей с действием «Показать ещё», сохраняя порядок и доступность всех уже загруженных путей. Построение путей итеративное и ленивое: сначала видимые раскрытые ветки, без материализации всех комбинаций общих детей. Нагрузка в BDD: 10 000 и 10 001 уникальный узел (включая 1000 корней), 50 000 и 50 001 уникальное ребро при числе узлов ниже предела, 200 и 201 путь отображения; глубокая цепочка и граф с общими потомками. Точные ожидания заданы в плане TDD. При обнаружении первого превышения лимита новых узлов/рёбер остановить расширение графа: новые объекты не ставятся в очередь, уже принятые получают доступные истории, пограничные ветки помечаются неполными. Повторы рёбер и ссылки нескольких родителей не увеличивают число уникальных объектов. Порция из 200 путей ограничивает вывод, а не полноту загруженного графа. Проверять ограниченность сетевой очереди, отсутствие переполнения стека и доступность следующих порций, а не неподтверждённый срок ответа.

Добавить отдельную фазу/счётчики чтения связей и историй дочерних объектов. Счётчик исходных HF не увеличивается. Сохранить предупреждения с ключом и кодом без PAT и содержимого credentials. Отдельное качество графа отражается в сводке; общий набор не называется полным при неизвестных ветках.
