# Проектирование: ввод нескольких ключей эпиков

Решение реализовано по прямому поручению пользователя; [протокол](verification.md) фиксирует результаты и оставшуюся визуальную проверку. Ниже сохранены исходный контекст и целевое решение изменения; `draft` не означает отсутствие кода и не подменяет формального согласования дизайна.

## Текущий и целевой потоки

### До изменения

```text
Много ключей → CSV/XLSX → API файла → кандидаты → Jira → расчёт → один набор → таблица
Один эпик → Jira-ссылка → отдельный API → Jira → расчёт → один набор → таблица
Ошибочные ключи файла → аудит; отдельной строки в общей таблице нет
```

### Реализованный поток

```text
Вставка текста → разбор строк и таблицы → кандидаты + ошибки строк → один API
             → тот же отбор и чтение Jira → тот же расчёт → один сохранённый набор
             → HF-эпики и ошибки в общей таблице; причины также в аудите
Обновить → сохранённые кандидаты + ошибки формата → новая проверка Jira → новый набор
```

## Контракты и совместимость

Предлагается `POST /api/keys/import` с JSON `{text: string}` и существующим `X-Local-Request: 1`. Ограничение тела остаётся 16 КиБ. Успех возвращает `202 {id}`; статус и аудит читаются через существующий `GET /api/jobs/:id`, итог — через `GET /api/dataset`. Пустой ввод возвращает понятную ошибку 400 до создания задания. Остальные маршруты, заголовок `X-History-Source` файла и автономный XLSX не меняются.

Маршрут принимает только объект с единственным строковым полем `text`: массив, `null`, отсутствующее поле, число и дополнительные поля отклоняются с 400; неправильный MIME — с 415, тело больше 16 КиБ — с 413. Ограничение относится к байтам UTF-8 всего JSON, поэтому 1000 ключей — дополнительный предел, а не обещание, что любой такой список поместится в запрос. Серверный парсер является единственным источником решений о валидности; браузер передаёт текст без извлечения только удачных ключей, иначе потеряются ошибочные строки. Парсер выполняется один раз до принятия задания для проверки пустоты и пределов; в задание передаются готовые кандидаты и ошибки. Доступ к Jira начинается только после принятия задания.

Граница разбора — предлагаемый метод `DatasetService.importKeys(text)`: после проверки занятости он вызывает парсер и передаёт результат в `startJira`. HTTP-обработчик проверяет только транспорт и форму JSON. `collectJiraInputs` получает разобранный ввод и повторно текст не разбирает; refresh использует сохранённые входы. Таким образом, вызовы сервиса в тестах и HTTP используют одну и ту же проверку пустоты/лимита кандидатов.

Разбор принимает одну строку с ключом, `| КЛЮЧ |`, пустые строки, подпись `New grid` перед таблицей и строку Markdown-выравнивания `| :--- |`. Копирование отображаемой колонки обычно даёт обычный построчный текст; оба вида представлены в [контрольных примерах](examples.md). Поддерживаются LF/CRLF, пробелы и табуляция по краям ячейки. Регистр ключей нормализуется. Иные непустые строки сохраняются как `invalid` с номером и причиной; многостолбцовая строка не дробится на несколько ключей. Первый ключ таблицы — данные. Повторы валидных ключей объединяются с сохранением всех номеров строк. Предлагается предел 1000 уникальных валидных кандидатов: превышение отклоняет весь ввод без усечения; существующий предел 1000 включённых HF также остаётся.

В [контракт источника](../../../../../../shared/contracts.ts) добавляется `kind: 'keys'` и время исходного ввода. В `JiraInputs` сохраняются нормализованные кандидаты и записи аудита ошибок; исходный многострочный текст не нужен для refresh. [Схема кэша](../../../../../../server/jira/cache-schema.ts) проверяет новый вид источника. Старые сохранённые наборы всех профилей читаются прежним способом. Новая версия файла кэша не нужна, так как `schemaVersion: 3` и `calculationProfile: jira-v3` сохраняются, а схема расширяется ещё одним вариантом источника.

Новый вариант источника содержит `kind: keys`, `importedAt` и `historyMode: jira`; `importedAt` сохраняет время исходного ввода и не сдвигается при refresh. `historyMode` означает выбранный способ получения истории, а не факт выполненного запроса. Ошибочный текст хранится только в `audit.entries`, где `requestedKey` допускает произвольную строку; массив `candidates` сохраняет существующую строгую проверку синтаксиса ключа. Для нового источника схема дополнительно проверяет: непустой аудит, непустые номера строк, запись решения для каждого корректного кандидата с его исходными номерами, отсутствие пересечения номеров ошибочных строк с номерами корректных кандидатов и соответствие включённых ключей `epics`. `inputRows` считает строки данных, поэтому не является верхней границей номера строки: ввод может содержать пропуски. Локальный отчёт только об ошибках имеет пустые кандидаты, эпики и истории и хотя бы одну запись `invalid`; пустой аудит не считается таким отчётом.

### Места интеграции нового варианта источника

| Место | Необходимое изменение |
| --- | --- |
| `SourceInput` и `SourceForm` | Добавить `keys` с текстом и многострочным полем; URL-проверка применяется только к доске/одиночному эпику |
| `App.startJob` | Сериализовать `{text}` отдельной веткой; существующая ветка `{url: source.url}` не подходит для списка |
| `JiraRequest`, `DatasetService`, `collectJiraInputs` | Передавать разобранный ввод и различать новый импорт/refresh; блокировка и публикация остаются в сервисе |
| `SourceDefinition`, `sourceSchema` | Согласованно добавить один и тот же вариант; одного изменения TypeScript-типа недостаточно для записи/чтения кэша |
| `DatasetSummary` и подпись среза в `App` | Явно обработать `keys`; существующий остаточный вариант `source.key` означает одиночный эпик и здесь неверен |
| `TimelineTable`, поиск и сортировка | Передавать представление ошибок наряду с эпиками; текущий `epics.map` их не отображает |

Изменения типов и потребителей проверяются вместе на T017. Проверка сборки сразу после расширения одного union до исправления остальных веток дала бы закономерные ошибки незавершённой интеграции.

## Данные, согласованность и конкурентность

Владелец текущего набора и единственная граница публикации — [DatasetService](../../../../../../server/service.ts) и [CacheStore](../../../../../../server/cache.ts). Новый запрос использует существующий mutex одного задания, общий `asOf` и запись через временный файл с переименованием. Новой таблицы, файла истории выборок и собственного расчёта нет. Ключи с валидным форматом проходят действующую группировку по стабильному `issueId`; повторные ключи не порождают несколько историй. `audit.inputRows` считает непустые строки данных без служебных строк; номера строк относятся к исходному тексту.

Парсер сначала создаёт корректных кандидатов и полноценные ошибочные записи (`requestedKey` с исходным текстом, `rows`, `decision: invalid`, `reason`). Для списка только из ошибок общий конвейер формирует частичный набор локально **до** `gatewayFactory` и чтения Keychain; схема допускает пустой `candidates` при непустом аудите ошибок. `asOf` и начало/конец обработки в таком наборе — локальные отметки задания, без утверждения о синхронизации Jira. Подпись источника сообщает «ошибки ввода; Jira не запрашивалась». Если вход пуст, API отклоняет его до задания.

Для `keys` `sourceCoverage` равно `complete`, если весь допустимый ввод разобран без усечения; `eligibilityCoverage` равно `partial` при наличии `invalid` либо `unresolved`, иначе `complete`. Это правило применяется только к новому источнику. Текущий `buildJiraDataset` уже делает набор с `invalid` частичным, но текущая сводка использует именно `eligibilityCoverage` и иначе ошибочно сообщит «нет подходящих HF». Метаданные отчёта только об ошибках подписываются как время проверки ввода и число ошибок; надписи «срез истории» и «история Jira» к нему не применяются. Локальный вариант определяется по `source.kind: keys` и непустому аудиту, состоящему только из `invalid`, без нового дублирующего флага.

Даже локальный отчёт проходит общий путь `startJira` → нормализованные входы → `buildJiraDataset` → `cache.write` → публикация состояния. Ранний выход из сборщика входов не должен напрямую менять текущий набор, обходить mutex или проверки отмены сервиса. `job.audit` заполняется также в локальной ветке. `completed` задания означает сохранённый отчёт; ошибки ключей читаются из аудита, а не только из `job.errors`: существующее заполнение этого массива включает лишь ошибки историй `dataset.epics` и для отчёта только из `invalid` остаётся пустым.

При наличии корректных ключей существующий итоговый барьер `SELECTION_UNRESOLVED` меняется только для `kind: keys`: отдельные неразрешённые кандидаты, в том числе весь список из них, не блокируют отчёт. Глобальные `JIRA_UNAUTHORIZED`, `PROFILE_UNVERIFIED`, `RATE_LIMITED` и отмена остаются ошибками всего задания. Нельзя применять это исключение к доске, файлу или одиночному эпику.

Для `kind: keys` неразрешённая задача и неверная строка остаются в аудите и в строке ошибки. Если есть пригодные HF, они показываются вместе с ошибками. Если валидные ключи есть, но все недоступны, либо остались только ошибочные строки, результат содержит ноль HF и видимый отчёт об ошибках. Такой результат не называется подтверждённым отсутствием HF. При отсутствии даже ошибочных строк новый набор не создаётся. Публикация при отсутствии доступной истории у **включённых HF** сохраняет действующий отказ: ошибки задания и аудит должны быть показаны, прежний набор остаётся.

Строки ошибок ключа являются представлением `invalid`/`unresolved` в [SelectionAudit](../../../../../../shared/contracts.ts), а не фиктивными `EpicTimeline`: числовые агрегаты, медиана, максимум и число HF вычисляются только по `dataset.epics`. В строке таблицы показываются исходное значение, номер строки, состояние «Ошибка» и причина, все числовые ячейки — прочерк; календарная область не рисует сегментов. Каждая ошибка формата сохраняет своё место ввода; для повторённых корректных ключей/алиасов Jira показывается одна строка на итоговую задачу или неразрешённый ключ, остальные вхождения видны в аудите. Идентификатор строки ошибки не совпадает с ключом реального эпика. React выводит исходный текст как текст, без интерпретации HTML.

Таблица строится и при пустом `dataset.epics`, без зависимости от наличия календарного диапазона. Отсутствующая дата либо число не превращается в ноль. Сортировка по числам ставит ошибки после известных значений, поиск по введённому тексту находит их. Скрытие по фильтру исполнителя допустимо лишь по явному выбору исполнителя; по умолчанию ошибки видны. Исходный порядок сохраняется во входах и аудите; порядок пригодных эпиков в отчёте задаётся действующей сортировкой TTM по убыванию. Ошибки при равенстве упорядочиваются по первому номеру строки.

Текущий `calendarRange([], asOf)` возвращает запасной диапазон, поэтому вводить новую модель отсутствующего диапазона не требуется. Важна явная отрисовка строк ошибок в `TimelineTable` и подавление сообщения «По этому запросу эпиков нет», если есть видимые ошибки. Запасной диапазон не означает наличие истории: в отчёте только об ошибках календарные деления и полосы не рисуются. Проекция строк имеет два различимых вида — эпик и ошибка; обработчики `onSelect`/`EpicPanel` вызываются только для эпиков. Сортировка не применяет числовое сравнение к тексту ошибки; при смене направления неизвестные значения остаются после известных. Счётчик ошибок и число видимых строк считаются отдельно от HF-метрик.

Подтверждённый HF с неполной историей остаётся `EpicTimeline` и учитывается как HF. Это не строка ошибочного ключа: доказанный TTM сохраняется при недоступном флаге, состояние `not-started` остаётся ожидаемым. Причины ошибок истории берутся из предупреждений эпика по действующему UI-контракту; правило отказа, когда недоступны все истории включённых HF, этим пакетом не меняется. Так сохраняется исходная граница пользовательского уточнения: вопрос и ответ касались неверных ключей.

Refresh копирует целиком исходные записи `invalid`, включая текст и причину, а не только их номера. Все синтаксически корректные кандидаты проверяются повторно по сохранённому `issueId`, если он известен, иначе по ключу. Новые решения `unresolved`/`included` формируются заново; устранённая ошибка не подмешивается из прошлого отчёта. Набор только с ошибками формата обновляется локально без Jira и не очищает эти строки. Для исправления требуется новый ввод.

## Обработка сбоев и восстановление

| Сбой | Обнаружение | Реакция | Повтор | Действие пользователя |
| --- | --- | --- | --- | --- |
| Неверный формат отдельной строки | Парсер текста | Ошибка в общей таблице, другие ключи продолжают обработку | Новый ввод после исправления | Исправить указанную строку |
| Пустой ввод | Нет строк данных или ошибок | HTTP 400, предыдущий набор сохранён | Новый ввод | Вставить ключи |
| Задача недоступна либо формат Jira неизвестен | Существующий адаптер/отбор | Строка ошибки с сообщением без чисел; другие кандидаты продолжают | Ручное обновление | Проверить ключ/доступ |
| Глобальный отказ PAT, профиль, лимит Jira | Существующий конвейер | Задание `failed`, прежний набор сохранён | После устранения причины | Проверить доступ |
| Нет истории ни у одного включённого HF | Существующее правило `HISTORY_UNAVAILABLE` | Задание `failed`; прежний набор сохранён, аудит доступен | После восстановления истории | Повторить |
| Ошибка записи либо перезапуск | CacheStore/потерянный job | Прежний сохранённый набор остаётся, UI восстанавливает его | Повторный запуск | Посмотреть сообщение |

## Безопасность и конфиденциальность

Сохраняются точная проверка `Host`/`Origin`/`Sec-Fetch-Site`, обязательный локальный заголовок POST, только серверное чтение PAT и ограниченные GET Jira. Поле ввода не отправляет запросов до явного запуска. Текст не должен попадать в URL или журналы с секретами. Кэш содержит ключи и метаданные задач, как и существующий файловый Jira-набор; права локального каталога остаются `0700`, файла `0600`.

## Наблюдаемость и производительность

Используются существующие фаза, прогресс, аудит и сообщения задания. Число уникальных кандидатов ограничено 1000, JSON — 16 КиБ, параллельных Jira-чтений — четыре. Дубли и ошибочные строки отражаются в аудите; обновление позволяет увидеть изменившуюся пригодность. Заявленного времени обработки или SLA нет: оно зависит от Jira, повторов и истории.

Живой прогон по приведённым ключам не является условием проверки формата. При отдельной живой приёмке объём чтения Jira должен быть согласован; синтетические тесты не доказывают доступность конкретных задач.

Команды выше относятся к завершённым слоям. Внутри TDD использовать адресные группы из [плана](tdd-plan.md), чтобы тест схемы не требовал ещё отсутствующего HTTP, а тест формы — готовой сводки. Итог проверки самих артефактов и исправленные риски записаны в [ревью реализуемости](implementation-review.md).

## Ввод в эксплуатацию и откат

Изменение включает только локальную форму, API и вариант источника в кэше v3. Выпускать вместе клиент и сервер, после прохождения регрессии. Старые наборы продолжают открываться новым кодом. Для отката к прежней сборке сначала восстановить прежний совместимый набор или резервную копию кэша: старая схема не знает `kind: keys` и не сможет прочитать новый такой набор. Автоматического обратного преобразования нет; до выпуска проверить этот сценарий на временном каталоге.

Источник обратимого восстановления должен существовать **до** первой записи `keys`: сохранить локальную копию прежнего `dataset.json` с правами `0600` и прежнюю рабочую версию приложения. Не использовать `dataset.v2.backup.json` как универсальную копию v3. HEAD не содержит всего нынешнего рабочего дерева, поэтому один `git checkout` на записанный commit не воспроизводит прежнюю сборку. При отсутствии прежнего набора откат проверяется с пустым каталогом. Проверку совместимости выполнить на отдельных временных каталогах со старым и новым кодом; реальный пользовательский кэш в проверке не перезаписывать. Пользователю новая версия не обещает автоматического чтения `keys` прежней сборкой.

## Решения и альтернативы

Пользователь подтвердил смешанный результат с отдельными ошибочными строками. Предлагается общий конвейер кандидатов и отдельный вариант источника, чтобы сохранить правила Jira и поддержку refresh. Альтернатива — синтезировать CSV в браузере и скрыто отправить в файловый маршрут — не хранит понятную идентичность прямого списка и вынуждает подменять ошибки и имя файла. Новый слой хранения не требуется. ADR не нужен: решение локально для одного источника и сохранено в архиве пакета по последующему [поручению пользователя](archive.md); визуальная проверка остаётся открытой.
