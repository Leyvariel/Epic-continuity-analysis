# TDD: порядок проверки и реализации

План использован после прямого поручения пользователя реализовать изменение. Фактические циклы, уже зелёные при добавлении проверки и оставшаяся визуальная проверка описаны в [протоколе](verification.md); ниже сохранён порядок разработки, а не утверждение о незапущенных тестах. Для одного наблюдаемого поведения из [BDD-карты](bdd-scenarios.md) добавить тест, увидеть ожидаемое падение, внести минимальное изменение до зелёного результата и затем упростить код с повторным прогоном. Не писать заранее весь набор падающих тестов для всех слоёв: это сделает промежуточные условия завершения невыполнимыми.

## Красная фаза и завершение задач

T011, T012 и T013 из [задач](tasks.md) закрывают только **первую красную проверку** парсера, схемы кэша и формы соответственно. Они завершаются свидетельством ожидаемого падения, не зависят от будущего зелёного прогона и не означают выполнения AC. Зелёный результат принадлежит последующей задаче реализации. Остальные тесты добавляются по одному непосредственно перед соответствующим изменением кода; T017 требует, чтобы в конце все они были зелёными.

Для отсутствующего модуля разрешена минимальная заглушка экспорта без реализации поведения; затем обязательно получить падение проверяемого утверждения. Ошибка импорта, timeout, опечатка в фикстуре или ноль выбранных тестов не подтверждают красную фазу. Если новая проверка уже зелёная благодаря существующему поведению, зафиксировать это как регрессию; не ломать код искусственно.

## Последовательность небольших циклов

Все перечисленные тестовые файлы созданы и исполняются; фактический результат указан в [протоколе](verification.md). Префиксы `KEYS-*` включать в `describe`/`it`; они соответствуют группам BDD-карты. Команды запускать из корня проекта. Каждый адресный запуск должен выполнить хотя бы один тест; он подтверждает только свой срез, а не весь AC или будущий файл.

## Фикстуры, асинхронность и связь слоёв

Использовать соответствие ключей/id и независимые числовые ожидания из BDD-карты. Не строить ожидаемый результат вызовом той же функции, которую проверяет тест. Для схемы готовить минимальные валидные входы и портить по одному инварианту; тест схемы не должен ждать ещё отсутствующий `importKeys` или маршрут. Обычные UI-тесты могут подменять fetch и получать синтетические наборы, но они не доказывают согласованность с HTTP-контрактом.

Для `tests/keys-flow.test.tsx` использовать существующие средства: jsdom/React из `tests/ui.test.tsx`, локальный HTTP-сервер с `createApp` из `tests/jira-api.test.ts`, настоящий DatasetService/CacheStore, подменённую только Jira и временный каталог. Адаптер fetch преобразует относительный URL в адрес локального сервера, сохраняя method, headers, body и signal; не создаёт ответы API сам. Проверить отправленный сырой текст, GET job/dataset, запись кэша и DOM с итоговыми строками. Это интеграционная проверка маршрута пользователя, не проверка CSS настоящим браузером.

В тестах сервиса ждать `service.waitForIdle()`, затем читать финальный job: обход с таймером 2 мс и 100 попытками из прежних тестов не копировать. Для mutex использовать управляемый Promise в gateway или записи кэша и обязательно освобождать его в cleanup. Отмену Jira-пути вызывать при удержанном чтении до commit; локального пути — сразу после принятия job, до первой микрозадачи. Не обещать откат уже начатой записи. В компонентных тестах допустимы fake timers, но прогон с реальным HTTP работает на реальных таймерах с ограниченным ожиданием условия; `now` сервиса остаётся фиксированным. В cleanup сначала размонтировать UI/остановить polling, освободить тестовые задержки, дождаться idle, закрыть сервер, затем удалить временный каталог и восстановить моки.

Реальная Jira, Keychain и личный кэш не используются. Общий `npm run check` не заменяет сквозные проверки: `KEYS-FLOW` должен существовать и реально исполняться в этом прогоне. До этого нет свидетельства, что форма и сервер одинаково понимают новый источник.

## Свидетельства проверки

После разрешения реализации создать `verification.md` с первой красной фазы и дополнять в ходе работы. T016 завершает этот файл визуальными проверками и откатом, не откладывает его создание до конца. Для каждого цикла фиксировать задачу/AC или группу `KEYS-*`, команду, число выбранных тестов, причину красного результата, зелёный результат и повтор после рефакторинга; для уже зелёной регрессии так и написать. Для T017 указать итог всех тестов/сборки, для T016 — снимки и результат восстановления. Файл свидетельств и исполняемые тесты созданы; автоматическая проверка пройдена, ручная визуальная проверка T016 остаётся открытой.
