# BDD: проверяемое поведение прямого ввода

Это карта проверок для [критериев приёмки](specs/source-selection.md), [жизненного цикла](specs/dataset-lifecycle.md) и [визуализации](specs/visualization.md). Нормативные требования остаются в дельта-спецификациях; здесь указаны конкретные условия, наблюдения и тестовые данные. Исполняемые проверки созданы; результаты прохождения и границы автоматических свидетельств записаны в [протоколе](verification.md). Отдельный исполняемый Gherkin-файл не нужен: в проекте принят Vitest, а названия тестов могут содержать AC-ID и шаги «дано — когда — тогда».

Каждый сценарий получает отдельный сервис/временный кэш или явно заданный прежний набор. Кроме проверки занятости, активного задания перед запуском нет; это важно для ожидаемых 400/409. Статусы завершения проверяются после ожидания задания, отдельно от немедленного ответа 202.

## Контракт синтетических данных и границ

- Точные 24 ключа используются **только для проверки разбора**. Их доступность, тип и историю в Jira тесты не предполагают. Для конвейера нужны синтетические `TEST-*` задачи и управляемый gateway из существующих `tests/jira-fixtures.ts`.
- `fakeGateway()` по умолчанию возвращает всем ключам `TEST-1` с `id: 10001`, а `jiraHistory()` тоже содержит ключ `TEST-1`. Для нескольких задач задать явное соответствие ключа и стабильного id: `TEST-1 → 10001`, `TEST-2 → 10002`, `TEST-3 → 10003`, `TEST-4 → 10004`. Ответы контрольного чтения по id и истории должны относиться к той же задаче. Совпадающий id использовать только в тесте алиасов; неизвестный ключ в заглушке должен приводить к явной ошибке теста.
- Для смешанного примера `TEST-1` — HF с полной историей из `jiraHistory()` и TTM 15 дней; `TEST-2` отдельно недоступен; `TEST-3` — DF. Ожидать один HF, две ошибки, медиану и максимум 15 дней при пустых фильтрах. Для сортировки добавить `TEST-4`: начало TTM 02.09.2026 09:00 UTC, завершение 07.09.2026 09:00 UTC, TTM 5 дней. Медиана двух HF — 10, максимум — 15 дней; ошибки в расчёт не входят. Ожидаемые числа заданы независимо от проверяемой функции расчёта.
- Зафиксировать часы и `asOf` через `AS_OF` из `tests/fixtures.ts`, использовать временный каталог кэша. Для refresh переключить набор ответов между завершёнными заданиями: `TEST-2` становится HF, прежний HF получает изменённую историю, DF повторно проверяется. Проверить новое вычисленное значение, отсутствие старой ошибки, неизменный `importedAt` и неизменные текст/причину/номера invalid. Для отчёта только из invalid отдельно проверить локальный refresh без gateway и новый исправленный ввод, который заменяет ошибку.
- Не требовать одного вызова `getIssue` на кандидата: текущий конвейер делает контрольные чтения и разрешает повтор при изменении задачи. Проверять состав кандидатов, стабильные id, отсутствие запросов ошибочного текста и число итоговых строк; один вызов истории на алиасы проверять только при стабильной полной истории без повтора.
- Отдельно проверять LF/CRLF, пробелы/табуляцию, первый ключ таблицы как данные, строку с несколькими колонками как **одну** ошибочную строку, номера после пустых строк, 1000 уникальных кандидатов и отказ на 1001-м без усечения. Тело JSON больше 16 КиБ отклоняется на транспортной границе; синтаксический лимит и лимит тела — разные проверки.
- API отклоняет неверный MIME (`415`), не-объект, отсутствие/нестроковое `text`, лишнее поле (`400`), слишком большое тело (`413`) и сохраняет требования к локальному заголовку. Ошибка транспорта не создаёт задание.
- Глобальный отказ авторизации, непроверенный профиль, лимит Jira и полная недоступность истории включённых HF оставляют задание `failed` и прежний набор. Их нельзя превращать в строки «не найден ключ». Устаревший `datasetId` по-прежнему даёт `409`.
- Строка ошибки отображает исходный текст безопасно как текст, без HTML; по умолчанию видна, а выбор строки не открывает панель эпика. Локальный отчёт только об ошибках не подписывается временем чтения Jira.

## Дополнительные проверки договора реализации

Они конкретизируют [дизайн](design.md), а не добавляют новые бизнес-требования. Имена групп нужны для адресного запуска тестов из [TDD-плана](tdd-plan.md).

| Группа | Что наблюдать | Связь и будущий файл |
| --- | --- | --- |
| `KEYS-PARSER` | Два блока из examples, нормализация/повторы, неверная многостолбцовая строка целиком; физические номера строк после пропусков. Ровно 1000 уникальных ключей принимаются, 1001 отклоняется до gateway; 1001 строка с повторами одного ключа не превышает предел уникальности | AC-018–021; `tests/key-candidates.test.ts` |
| `KEYS-CACHE` | Смешанный и локальный набор проходят схему и чтение. Нет кандидата без решения, пересекающихся номеров invalid/candidate или included без соответствующего эпика; пустые epics и candidates допустимы при непустом invalid-аудите. `inputRows` не ограничивает максимальный физический номер строки. Прежние варианты кэша читаются | FR-028, AC-024; `tests/keys-service.test.ts`, существующий `tests/cache-v3.test.ts` |

Локальная ветка не создаёт gateway, все недоступные ключи не вызывают общий отказ. DF, отклонённые и неэпики остаются исключениями аудита | FR-027/029, AC-020/021/025/027; `tests/keys-service.test.ts` |
| `KEYS-SERVICE` | Job завершён только после записи. При занятом сервисе новый ввод получает `BUSY` (409); отказ записи и отмена **до начала commit** сохраняют прежний набор, после освобождения блокировки следующий ввод работает. | `KEYS-API` | JSON-массив, null, пропущенное/нестроковое text, лишнее поле, испорченный JSON → 400; MIME → 415; нет локального заголовка → 403. Отдельно проверить 16384 и 16385 байт **всего** UTF-8 JSON с допустимым числом кандидатов: первый не отклоняется по размеру, второй → 413. Отказы не заменяют прежний набор и не обращаются к gateway. Сохранить `STALE_DATASET` и `OFFLINE_SOURCE` (409) | FR-001/021/027, AC-021/022; `tests/keys-api.test.ts` |
| `KEYS-FORM` | Поле передаёт исходный текст callback один раз; до отправки callback не вызван; состояние busy блокирует повторную отправку | FR-026, AC-022; `tests/keys-ui.test.tsx` |
| `KEYS-TABLE` | Поиск и сортировка проверяются отдельно; ошибки не открывают EpicPanel, не становятся HTML и не дают чисел/полос. При пустом фильтре исполнителя ошибки видны. Проверить две одинаковые неверные строки: обе видны со своими номерами. Нет ложного сообщения «эпиков нет» | FR-029, AC-025–028; `tests/keys-ui.test.tsx` |
| `KEYS-SUMMARY` | HF-счётчик, счётчик ошибок и агрегаты различаются; локальный отчёт не утверждает чтение Jira. Неполный флаг не стирает известный TTM; not-started не превращается в ошибку ключа | FR-029, AC-021/025/027/028; `tests/keys-ui.test.tsx` |
| `KEYS-FLOW` | Реальная форма → HTTP JSON → сервис → синтетическая Jira/локальная ветка → временный кэш → polling → таблица. Минимум смешанный и полностью ошибочный ввод; проверить автоматический показ, один POST, содержимое GET dataset и видимые строки | AC-020/021/022/025; `tests/keys-flow.test.tsx` |

В полностью ошибочном отчёте ноль HF допустим в счётчике. Запрет чисел относится к метрикам ошибочных строк и отсутствующим агрегатам; не проверять отсутствие любых цифр во всём DOM: ключи, номера строк и время проверки сами содержат цифры. Полосы/деления проверять внутри таблицы, а не по всему приложению. Точную русскую формулировку причины не закреплять, кроме явно заданных надписей; проверять, что она непустая, соответствует типу сбоя и не выдаёт «не найдена или недоступна» за доказанное удаление задачи.

Считается проверенным только поведение, подтверждённое будущими тестами и ручным просмотром по [плану TDD](tdd-plan.md). Этот документ не меняет статус `draft`/`proposed` пакета и не является разрешением на реализацию.
