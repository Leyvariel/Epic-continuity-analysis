# Проверка реализуемости изменения

Историческая проверка подготовки пакета **до реализации**. Ссылки на код ведут в текущее рабочее дерево, а описанные ниже исходные ограничения относятся к прежней версии. Последующее состояние: [протокол реализации](verification.md) и [сверка текущей SDD](sdd-review.md).

## Итог

Изменение реализуемо в существующей архитектуре. Новый расчёт TTM, отдельное хранилище или новый Jira-адаптер не требуются. Проверка обнаружила конкретные риски интеграции, перечисленные ниже; решения внесены в [дизайн](design.md) и [задачи](tasks.md). Это проверка плана на актуальном коде. Сам новый ввод, маршрут и тесты ещё не реализованы, поэтому утверждение об отсутствии дефектов готового приложения было бы преждевременным.

## Проверки на текущих функциях

Без сети, Keychain и записи пользовательского кэша выполнен вызов существующих `jiraInputsSchema`, `buildJiraDataset` и `calendarRange` через `node --import tsx`. Синтетический вход использовал поддерживаемый файловый источник, ноль эпиков и одну запись invalid с текстом «неверный ключ».

| Наблюдение | Результат |
| --- | --- |
| Сохранение исходного неверного текста в аудите | Сохраняется |
| Общее качество набора | `partial` |
| Переданное `eligibilityCoverage: complete` | Остаётся `complete`; сборка набора его сама не исправляет |
| Ошибки через существующую проекцию предупреждений эпиков | Пустой массив |
| `calendarRange` для нуля эпиков | Возвращает запасной диапазон; новый тип nullable-диапазона не нужен |
| Подстановка нового `source.kind: keys` в действующую схему | Отклоняется, как и ожидается до реализации |

Оба контрольных примера помещаются в предложенный предел тела запроса: обычный список — 361 байт JSON UTF-8, Markdown — 473 байта. Проверка выполнена для точных блоков из [примеров](examples.md), без запросов указанных задач Jira. Это не нагрузочная проверка максимального объёма.

## Что остаётся проверить после реализации

После первоначальной проверки реализуемости структурная проверка пакета прошла с 0 предупреждений. Повторная проверка TDD/BDD включает структуру, локальные ссылки, граф 17 задач и смысл их условий завершения. Эти проверки относятся к пакету, а не к ещё отсутствующему коду нового ввода.

T017 должен подтвердить компиляцию, сборку и регрессию всех источников; новые тесты должны проверить вход только из ошибок, 403/404 по каждой задаче, глобальный отказ, однократный разбор, восстановление кэша, обновление исчезнувших ошибок и отсутствие дублей. T016 должен подтвердить видимый результат и обратимость на тестовых данных. Текущая техническая проверка не заменяет эти действия и не переводит пакет в approved.
