# Проектирование учёта работы и сброса данных

## Основание и состояние

Репозиторий `.`; исходная ревизия и незакоммиченные изменения указаны в [исследовании](research.md). Бизнес-решения Q1, Q2 и Q4 в [предложении](proposal.md) закрыты. Ниже описаны выбранные правила двух областей оценки и технический дизайн; его подготовка не означает выполнения реализации.

## Данные и текущий поток

`server/jira/sprints.ts` собирает историю поля Sprint и признак полноты. `server/sprint-analysis.ts` извлекает точную активность задач/подзадач, затем превращает её в покрытие целых спринтов. `server/sprint-focus.ts` оценивает циклы реализации. Календарь отсутствует даже у задачи с полной историей, если Sprint ID никогда не было; на исходной ревизии это ошибочно блокировало весь смешанный эпик.

Существующий владелец сырых данных — атомарно публикуемый набор. Новый результат использует сохранённые истории и подтверждённую классификацию проектов. Источник классификации — решение пользователя (Q2); состав определён в FR-054. Для реализации предлагается одна константа со списком ключей проектов в `server/sprint-analysis.ts`, используемая при выборе режима. Ключ проекта извлекается из ключа задачи и сравнивается с явным списком; пустое поле задачи не расширяет его. Изменение входного формата или кэша для хранения списка не требуется. Запись в Jira и изменение историй не нужны. Автономная книга и старый кэш без входов спринтов не доказывают отсутствие участия.

## Предлагаемый поток

1. Проверить, что проект подтверждён как работающий без спринтов; спринтовые и неклассифицированные проекты остаются на прежнем пути. Пустая выборка Sprint не подтверждает режим всего проекта. Затем проверить непротиворечивость полной истории членства задачи. Определить наличие хотя бы одного Sprint ID до общего среза, включая исходное состояние. Будущая принадлежность не меняет прошлый режим. Пустое текущее поле не отменяет прежних включений.
2. Только для подтверждённого проекта без спринтов и при доказанном отсутствии участия получить точные положительные и возможные активные интервалы по существующему правилу текущих подзадач. Не требовать календарь для этой задачи. Для задач с прежними спринтами сохранить существующий путь; при неполной истории не применять альтернативу.
3. Передать неспринтовую активность отдельно от `SprintSegment`: её нельзя представлять как положительный спринт. Сохранить даты и ключи источников для объяснения. Пересечения объединять, не суммировать повторно.
4. В смешанном эпике числовое покрытие равно объединению рабочих спринтов и точных активных интервалов без спринта. Область оценки остаётся внутри известных календарей и циклов реализации без Отложено. Прежняя отметка использует включение спринтовых задач плюс точные активные интервалы неспринтовых; не менять критерий членства для спринтовых задач.
5. Неизвестность неспринтовой активности ограничивается её возможными интервалами. Доказанная работа любой ветки сохраняется. Неизвестность членства или неполной ветки по-прежнему может затрагивать весь корень.
6. При полном составе и наличии хотя бы одной допустимой обычной задачи, когда каждая удовлетворяет FR-054, полностью неспринтовый эпик оценивается на всём доказанном цикле без Отложено; из него вычитается объединение точных активных интервалов. Повторные циклы, срез и окончательное закрытие определяются прежним FR-049. Пустая или неполная ветка не включает этот режим. Точные активные интервалы сами по себе не являются предварительными: будущая работа не покрывает прошлый простой задним числом.

## Интерфейс, ошибки и совместимость

`src/SprintFocusDetails.tsx` объясняет оба источника покрытия и перечисляет точные интервалы с ключами задач. `src/App.tsx` показывает правдивое значение отметки и уточняет «Без разрывов» до «Полная история». Новый способ не создаёт искусственных спринтов и не возвращает скрытые пустые сегменты. Название колонки — «Без работы»: детали показывают, оценивается ли весь цикл или только его часть внутри календарей. Внутренний идентификатор метрики можно сохранить; это не новая колонка рядом с прежней.

При недоступных статусах, неизвестной категории, неполном составе подзадач или обнаруженном переносе сохраняются соответствующие причины и известные части. Отказ загрузки не запускает альтернативный режим по отсутствующему полю. Повторный расчёт на тех же входах детерминирован; он не добавляет конкурирующих записей. Секреты и новые права не требуются.

## Проверка и ввод

FR-054 / AC-139, AC-140, AC-141, AC-142, AC-143 проверяются отдельными синтетическими тестами членства, статусов, пересечений, среза и подзадач. AC-144 воспроизводится на сохранённом HOTELS-13142 без изменения кэша. Браузер проверяет два уровня, масштабы, отметку и объяснение. Перед вводом: `npm run check`, структурная проверка SDD и проверка готовности полного пакета. Основной сервер перезапускается с прежним разрешённым доступом; для принятого списка проектов новое чтение Jira не требуется. Откат ограничен этой поправкой, чужие незакоммиченные изменения сохраняются.

Новый ADR пока не предлагается. Универсальность по задачам отменена; применяется явный список FR-054 по решению пользователя. Автоматическое добавление проектов по пустым полям Sprint исключено. Сохранённая выборка остаётся свидетельством наблюдений, а основание для режима проекта — согласованный список.


## Сброс данных анализа — FR-055

Текущие владельцы: `CacheStore` в `server/cache.ts` сохраняет один `dataset.json`, при миграции — `dataset.v2.backup.json`, при записи — `dataset-<UUID>.tmp`; `DatasetService` в `server/service.ts` хранит текущий набор, ошибку кэша, задания и признак занятости. На исходной ревизии метод сброса и маршрут отсутствовали; реализация по этому дизайну подтверждена в [протоколе](verification.md). `src/App.tsx` владеет фильтрами, масштабом, карточкой и опросом заданий; `src/SourceForm.tsx` хранит введённые ключи, ссылку и выбор режима. Данные браузера через localStorage/IndexedDB не сохраняются.

Предлагаемый локальный контракт: `POST /api/reset`, JSON `{datasetId: string | null}` и существующий заголовок `X-Local-Request: 1`. `datasetId` фиксируется при открытии подтверждения. `null` используется только при отсутствии читаемого набора, в том числе при ошибке кэша. Для нового пригодного набора несовпадение возвращает `STALE_DATASET` (409). Успех — `{dataset: null}`; повтор в уже пустом состоянии безопасен, старый ID не может удалить новый набор. Внешние источники, неверный формат и режимы просмотра отклоняются существующей защитой. Нового внешнего API нет.

Сервис проверяет занятость и ожидаемый набор до изменения файлов, затем занимает тот же эксклюзивный участок, что импорт и обновление. Импорт, refresh и второй сброс во время очистки получают `BUSY`. Активное задание не отменяется: пользователь ждёт завершения и затем сбрасывает набор. Это сохраняет существующую модель одного процесса и одного задания.

`CacheStore.clear()` удаляет только принадлежащие кэшу наборы: известную копию v2 и файлы записи с точным шаблоном имени UUID, затем `dataset.json` последним. Отсутствующий файл считается уже удалённым. Каталог целиком не удаляется: `jira-profile.json`, диагностические материалы и посторонние файлы сохраняются. Кэш не читается и не мигрирует перед удалением, поэтому доступен сброс повреждённого файла. При ошибке до удаления текущего файла он сохраняется; вспомогательные копии уже могли быть удалены, что не выдаётся за успешный сброс. После успешного удаления текущего файла сервис синхронно очищает `state`, `cacheError`, карту jobs и ссылки на завершённое задание; только затем отвечает успехом. При перезапуске отсутствующий файл означает пустое состояние. Действующие ограничения отсутствия межпроцессной блокировки и `fsync` не расширяются.

Кнопка размещается в верхней панели основного приложения, доступна также при пустом наборе и ошибке чтения кэша после завершения начальной загрузки. Во время импорта, обновления или сброса она заблокирована с объяснением. Предлагаемый текст подтверждения: «Сбросить все данные анализа? Сохранённый набор будет удалён. Чтобы вернуть его, потребуется загрузить данные заново». Действия — «Отмена» и «Сбросить данные»; закрытие окна эквивалентно отмене, клавиатурный фокус возвращается на кнопку. В продуктовый текст не выводятся имена файлов и детали серверной очистки.

До успешного ответа текущие данные не очищаются оптимистично. Во время сброса остальные действия загрузки заблокированы. Успех отменяет опросы, меняет поколение клиентских запросов и игнорирует ответы предыдущего поколения. `dataset`, job, карточка, сообщения, поиск, исполнитель, выбор метрик сбрасываются; сортировка возвращается к TTM по убыванию, масштаб — к неделе. Таблица размонтируется, сбрасывая раскрытие и прокрутку; `SourceForm` пересоздаётся с пустыми полями и стандартным выбором «Файл / История из Jira». После этого показано «Данные сброшены. Выберите источник для нового анализа».

При сетевой ошибке ответа выполняется чтение `/api/dataset`: пустое состояние завершает очистку UI, существующий набор остаётся видимым; при повторной недоступности сервера сообщается, что результат не подтверждён. Нельзя восстанавливать старый набор из задержавшегося ответа или автоматически повторять импорт. Другая открытая вкладка не обязана обновиться мгновенно, но её устаревший запрос не удаляет новый набор, а перезагрузка получает актуальное состояние.

Сопоставление требований: FR-055 / AC-145, AC-146, AC-147, AC-148, AC-149, AC-150, AC-151, AC-152 — T007, T008, T009, T010; исключение из FR-023 / сохранение AC-015 — T007, T008; перенос в текущую SDD и завершение — T006. Тесты выполняются на временных наборах; браузерные проверки — на отдельном экземпляре приложения с временным каталогом. Рабочий набор пользователя не сбрасывается ради проверки. После проверки в current specs переносится дельта `dataset-lifecycle.md`, а в operations — точная область удаления и восстановление. Реализация сервера и интерфейса проверена по этому дизайну; рабочий кэш не изменён. Итог сохранён в [протоколе](verification.md).
