# План TDD и BDD и фактическое выполнение

## Статус и источники

Документ добавлен 18.11.2026 после реализации по поручению пользователя оформить работу согласно договорённостям разработки. Он связывает существующие требования, тесты и свидетельства. Наличие этого документа не означает, что план был подготовлен до реализации или отдельно согласован пользователем.

Каноническое поведение — [текущая спецификация](../../../../specs/application-runtime.md), исходная дельта — [требования пакета](specs/application-runtime.md). Идентификаторы AC-160–AC-163 здесь относятся к возможности `application-runtime` и этому пакету; совпадающие номера сценариев других возможностей не обозначают те же проверки.

## Фактический цикл TDD

1. До реализации созданы проверки API и ожидания клиента. В [падающем запуске](evidence/red.txt) три проверки API получают 404 вместо 202/409. Клиентский файл тестов не загружается из-за отсутствия `src/restart.ts`: это свидетельство отсутствующего модуля, а не три выполненных падающих сценария клиента. Четвёртая проверка API проходит на существующей защите запросов; сама по себе она не доказывает наличие маршрута перезапуска.
2. Добавлены серверный перезапуск, ожидание клиента и кнопка. Первые семь проверок API/клиента проходят; результат последующего запуска всех четырёх файлов сохранён в [успешном запуске](evidence/green.txt).
3. После реализации добавлены UI и интеграционные проверки настоящего процесса. Их предварительного падающего запуска нет. Это проверки результата после реализации; полный цикл «падающий тест → реализация → успешный тест» для них не зафиксирован.
4. Выполнены общая регрессия, TypeScript, сборка, Chrome и визуальный осмотр. Сохранены [общий журнал](evidence/check.txt), [браузерный отчёт](evidence/visual/browser-report.json) и снимки. При текущем оформлении исторические журналы не заменяются новыми.

Таким образом, предварительный план TDD/BDD не был оформлен отдельным артефактом; оформить его задним числом как заранее выполненный этап нельзя. Этапы и ограничения учтены в [сверке разработки](workflow-review.md).

## Сквозные сценарии BDD

Это детализация сценариев действующей спецификации для проверок, а не дополнительные бизнес-требования.

### AC-160: Перезапуск с возвратом анализа

- **ДАНО** локальное приложение с сохранённым набором и доступной кнопкой.
- **КОГДА** пользователь нажимает «Перезапустить приложение».
- **ТОГДА** он видит ожидание; серверный процесс меняется; страница обновляется после ответа нового экземпляра и показывает тот же набор. Файл кэша сохраняется побайтно.

Свидетельства: оба режима в интеграционном тесте и последняя группа [проверки Chrome](evidence/visual/browser-report.json). Вариант полностью пустого состояния покрыт API/UI по частям; отдельного сквозного перезапуска пустого настоящего сервера нет.

### AC-161: Конкурентное действие

- **ДАНО** незавершённый импорт, сброс либо уже принятый перезапуск.
- **КОГДА** поступает конкурирующий запрос.
- **ТОГДА** он получает отказ, текущая операция продолжается; повторное нажатие и новый импорт из интерфейса заблокированы.

Свидетельства: API и UI. Отдельный сценарий обновления Jira не запускался; блокировка обновления и импорта использует общий признак занятости `DatasetService`.

### AC-162: Режим просмотра и локальность

- **ДАНО** режим demo/snapshot, внешний Origin либо отсутствие обязательного локального заголовка.
- **КОГДА** пользователь открывает страницу или отправляет запрос перезапуска.
- **ТОГДА** просмотр скрывает кнопку, а запрещённый запрос отклоняется до вызова перезапуска.

Свидетельства: API и UI. Прямой POST проверен в snapshot, отсутствие кнопки — в обоих режимах. Проверки Host и Sec-Fetch-Site остаются общей защитой API; отдельного нового сценария этих заголовков для маршрута перезапуска нет.

### AC-163: Отказ или недоступность

- **ДАНО** отказ POST, ответ старого экземпляра либо временная недоступность сервера после принятия запроса.
- **КОГДА** интерфейс выполняет перезапуск.
- **ТОГДА** отказ отображается сразу; принятый запрос ожидает новый экземпляр до тайм-аута, без автоматического повторного POST и без ложного успеха.

Свидетельства: клиентские проверки отказа, временного сбоя и тайм-аута; UI проверяет сообщение и снятие блокировки; Chrome проверяет отказ при видимом анализе. Тайм-аут проверен с управляемым временем, а не ожиданием 30 секунд в Chrome.

## Повторная проверка

Целевые тесты: `npm test -- --run tests/restart-api.test.ts tests/restart-client.test.ts tests/restart-ui.test.tsx tests/restart-runtime.test.ts`.

Общая проверка: `npm run check`. В текущем документальном дополнении её результат записывается отдельно в `evidence/retrospective-check.txt`.

Браузер: `node scripts/verify-restart-browser.mjs <отдельный-каталог-свидетельств>`. Он использует временный набор; обычное приложение и Jira не меняются. При документальном дополнении браузер не перезапускался: используется сохранённый результат реализации и прежний визуальный осмотр снимков.
