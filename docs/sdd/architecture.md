# Архитектура приложения

## Контекст

Один локальный процесс Node.js обслуживает React-интерфейс и API через Express. Браузер обращается к нему по `127.0.0.1`; только сервер читает PAT из Keychain и выполняет GET к фиксированному адресу Jira. Последний нормализованный набор хранится на диске. Основания: [запуск](../../server/index.ts), [API](../../server/app.ts), [клиент Jira](../../server/jira/client.ts).

## Контейнеры и зависимости

| Участник | Направление и протокол | Ответственность |
| --- | --- | --- |
| Интерфейс `src/` | Браузер → локальный сервер, HTTP | Выбор источника, запуск задания, прогресс и результат |
| API и сервис `server/` | HTTP → обработка в Node.js | Проверка локальности, одно активное задание, сохранение набора |
| Адаптер `server/jira/` | Сервер → `hq.tutu.ru`, HTTPS GET | Доска, задачи, история и полнота |
| Keychain macOS | Сервер → системная утилита `security` | Выдача PAT серверному процессу |
| `.local-data/dataset.json` | Сервер → локальный файл | Исходные данные и последний результат |

## Поток выполнения

Пользователь выбирает файл, прямой список ключей, доску или эпик. API создаёт задание; сервис фиксирует общий момент `asOf`, определяет кандидатов, проверяет их по Jira, читает историю подходящих задач, рассчитывает шкалы и записывает кэш. Список только из ошибочных строк сохраняется локально без Jira и Keychain. После сохранения интерфейс получает новый набор. Ошибка оставляет прежний набор; после перезапуска задания в памяти исчезают, но кэш восстанавливается ([сервис](../../server/service.ts), [конвейер](../../server/jira/pipeline.ts), [кэш](../../server/cache.ts)).

Отдельная совместимая ветка локального API читает старую XLSX-книгу с агрегатами и необязательными листами истории, строит `legacy-v2` и сохраняет его в оболочке кэша v3 без сети. React-форма файла по умолчанию выбирает Jira-ветку и позволяет явно выбрать автономную XLSX-ветку. Обе ветки используют общий расчёт интервалов, но только Jira-нормализация разрешает «Решили делать» как предрабочее состояние ([совместимость](specs/legacy-compatibility.md)).

Связи и истории потомков загружаются до атомарной публикации набора, а раскрытие не выполняет сетевых запросов. `server/jira/hierarchy.ts` получает направленный граф с дедупликацией по Jira-ID и ограниченной очередью; `server/table-hierarchy.ts` получает автономный эквивалент. `server/related-timeline.ts` рассчитывает полный жизненный цикл отдельно от TTM корней. `shared/hierarchy-view.ts` проецирует видимые ветки, `src/HierarchyRows.tsx` и `src/RelatedStatusBar.tsx` показывают их на общей оси. В кэше хранится проверяемое дополнение версии 1; производные полосы заново строятся при восстановлении. Интерфейс разделяет исходные эпики и дочерние строки, статистика считает только исходные.

## Локальный API

| Метод и путь | Вход | Успешный ответ |
| --- | --- | --- |
| `GET /api/dataset` | Без тела | 200, `{dataset: null}` либо сохранённый набор |
| `GET /api/jobs/:id` | Идентификатор задания | 200, объект задания со статусом, фазой, прогрессом, аудитом и результатом |
| `POST /api/import` | Сырые байты, `X-File-Name` с URI-кодированным именем; `X-History-Source: jira` для чтения Jira либо `file` для автономного XLSX | 202, `{id}` |
| `POST /api/keys/import` | JSON с единственным строковым полем `text` | 202, `{id}` |
| `POST /api/board/import` | JSON только с `url` | 202, `{id}` |
| `POST /api/epic/import` | JSON только с `url` | 202, `{id}` |
| `POST /api/refresh` | JSON только с `datasetId` | 202, `{id}` |

Все POST требуют `X-Local-Request: 1`. Для файла допустимы `application/octet-stream`, MIME XLSX и `text/csv`, предел 20 МиБ; без имени используется `import.xlsx`. Отсутствующий `X-History-Source` либо значение `file` выбирает старый автономный XLSX-контракт. JSON требует `application/json`, предел 16 КиБ.

Ошибки HTTP имеют форму `{error: {code, message}}`: 400 для неверных данных/JSON, 403 для нарушения локальности, 404 для потерянного задания, 409 для конфликта/устаревшего набора/автономного refresh, 413 для большого тела, 415 для неподходящего типа, 500 для внутренних сбоев и кэша. Ошибка уже принятого задания сообщается статусом `failed` в ответе polling, а не новым HTTP-статусом исходного POST. Синхронная проверка legacy-книги и разбор прямого списка могут отклонить запрос до 202; Jira-парсер файла выполняется внутри принятого задания. Исчерпывающие определения: [API](../../server/app.ts), [сервис](../../server/service.ts), [контракты](../../shared/contracts.ts).

## Разделение модулей

`server/file-candidates.ts` читает ключи файла, `server/key-candidates.ts` разбирает прямой текст; `server/jira/pipeline.ts` управляет отбором и повторами; `adapter.ts` и `board.ts` проверяют внешний формат; `normalize.ts` доказывает согласованность истории; `server/timeline.ts` рассчитывает интервалы. `shared/` задаёт типы, статусы, метрики и модели диаграмм; `src/` отвечает за состояние интерфейса, таблицу и детали. Zod проверяет ответы/кэш, SheetJS — книги и CSV, Express — HTTP, React — UI, Vite — разработку и сборку ([зависимости](../../package.json)).

## Ограничения

- Jira REST не даёт атомарного снимка доски и всех историй; приложение повторно проверяет состав **до** чтения историй и проверяет метаданные каждой включённой задачи после её истории. Финального перечитывания доски после всех историй нет. Поля `syncStartedAt` и `syncFinishedAt` обозначают окно наблюдения, а не гарантию атомарности.
- Параллельно выполняется одно задание; чтение задач и историй ограничено четырьмя запросами ([очередь](../../server/jira/concurrency.ts)).
- Профиль машины не входит в Git. Новая доска или изменённые постоянные настройки требуют отдельной диагностики.
- Это локальное веб-приложение, а не нативная программа macOS; сборка создаёт интерфейс в `dist/`.

Стандартный состав Epic Link адаптер получает отдельным постраничным чтением Jira Software API и объединяет с issuelinks до передачи в очередь графа. Повторная связь дедуплицируется по ID; ошибки состава не стирают доступные явные связи. Проверка стабильности включает повторное чтение обоих источников состава.

## Дополнение: анализ спринтов

После прежнего основного графа `collectJiraInputs` вызывает необязательный порт `readSprintInputs`. `ServerJiraAdapter` реализует его через `server/jira/sprints.ts`: обнаружение Sprint, стабильное чтение членства и native roster, истории подзадач, отдельная пагинация календаря по `isLast`. Фазы выполняются последовательно, в каждой не более четырёх одновременных запросов. Основные рёбра и полнота не пересчитываются из-за аналитики.

Входы содержат необязательное `sprintInputs` версии 1. Истории подзадач находятся в `HierarchyInput`, аналитические отношения — в дополнении. `buildJiraDataset` вызывает чистый `analyzeSprints`; результат `sprintAnalysis` не считается доверенным содержимым кэша и восстанавливается из входов. Публикация использует прежнюю атомарную запись `CacheStore`.

`SprintRows` подключён независимо от полноты статусной полосы на всех трёх уровнях. Параллельные спринты получают отдельные дорожки, а известные границы включаются в общую ось до раскрытия. Под полосой этапов отображаются только доказанные бреши по членству; предварительные состояния активного спринта и неизвестность остаются в сегментах спринтов. Эти слои независимы от числовых TTM/CT. Цвета этапов сохраняются также в календарном представлении при неизвестном TTM. Числа известных этапов полной Jira-истории вычисляются независимо по FR-041/AC-092.
