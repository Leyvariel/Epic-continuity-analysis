# Работа над изменениями

## Источники истины

- `docs/SDD.md` — точка входа в документацию.
- `docs/sdd/specs/` — текущее реализованное поведение.
- `docs/sdd/changes/` — активные change-пакеты и свидетельства проверок.
- Явные решения пользователя имеют приоритет; отражать их в документации.
- Не дублировать бизнес-правила расчёта в AGENTS.md.
- Запуск приложения и доступ к Keychain описаны в [инструкции эксплуатации](docs/sdd/operations.md).

## Цикл разработки

1. Зафиксировать желаемое поведение, примеры, границы и ошибки.
2. Через skill `sdd-writer` подготовить или обновить change-пакет:
   предложение, дельты требований, дизайн и задачи.
3. Проверить реализуемость по текущему коду и зависимостям.
4. Подготовить TDD и BDD с трассировкой требований к проверкам.
5. Получить разрешение на реализацию и разрешить блокирующие вопросы.
6. Выполнить цикл «падающий тест → реализация → успешный тест»,
   необходимые регрессионные и визуальные проверки.
7. Перенести проверенное поведение в текущую SDD.
8. Зафиксировать итог и архивировать пакет только при выполненных
   условиях завершения.

Согласование пакета и разрешение реализации учитывать по текущему
диалогу. Повторно разрешение на тот же объём не запрашивать.
При существенном изменении объёма или поведения согласовать отличие.

Небольшие исправления в рамках активного изменения вести в том же
пакете, сохраняя требования и свидетельства предыдущих проверок.

## Проверки и свидетельства

- Для изменений поведения сначала воспроизвести проблему тестом.
- Для изменений интерфейса проверить результат в браузере,
  включая затронутые масштабы, раскрытие и прокрутку.
- Проверка DOM не заменяет визуальную проверку.
- Перед завершением выполнить `npm run check` и валидацию SDD.
- Сохранять результаты проверок и снимки в `evidence/` пакета.
- Не отмечать невыполненные проверки выполненными.
- Завершение отдельного исправления не означает приёмку всего пакета.
- Архивировать с незавершёнными проверками только по явному
  решению пользователя.

## Данные и рабочее окружение

- Сохранять несвязанные пользовательские изменения.
- Для проверки отображения использовать сохранённый набор,
  если свежие данные не требуются.
- Не менять расчёты, историю и сохранённые данные ради исправления UI.
- Не выводить PAT и другие секреты в логи, тесты или документацию.
- Не выполнять commit и push без поручения пользователя.

## Коммуникация

На каждом этапе сообщать коротко:
**что завершено → что осталось → следующий шаг**.

В итоговом сообщении указывать фактический результат, выполненные
проверки, ограничения и оставшуюся работу.
