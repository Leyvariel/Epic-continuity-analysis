# Анализ HF-эпиков

Локальное приложение для macOS: календарная история эпиков, длительности этапов, heatmap, возвраты в Открыто и impediment. Четыре источника выборки: файл CSV/XLSX, прямой список ключей, ссылка на Jira-доску, ссылка на отдельный эпик. В Jira-режимах история и текущие признаки берутся из Jira. В форме файла также доступен автономный XLSX со связями и историей; этот режим и просмотр сохранённого результата работают без сети.

## Запуск

Нужен Node.js 22.12 или новее. Зависимости в этом рабочем каталоге установлены.

```sh
npm run dev
```

Открыть **http://127.0.0.1:4317**. Сервер слушает только `127.0.0.1`. Для другого порта: `PORT=4318 npm run dev`.

На новой копии проекта сначала выполнить `npm ci`. Для собранного интерфейса:

```sh
npm run build
npm start
```

После изменения серверного кода остановите прежний процесс (Ctrl+C) и запустите его снова.

Проверочные серверы `verify-hierarchy-demo.ts` (4329) и `serve-snapshot.ts <каталог снимка>` (4330) работают только для просмотра: показывают явное предупреждение и ссылку на основное приложение, не предлагают загрузку и обновление, отклоняют изменяющие запросы API. Ввод реальных ключей выполняется в основном приложении на 4317.

## Работа с источниками

- **Файл:** CSV UTF-8 или XLSX, достаточно колонки `Ключ`, `Ключ эпика`, `Ключ проблемы`, `Issue key` или `Key`. Поддерживается одноколоночный список без заголовка. Например: заголовок `Ключ`, следующая строка `HOTELS-13561`. Несколько листов выборки или колонок ключей требуют устранить неоднозначность. Название, тип, resolution и история в файле не обязательны. Необязательные агрегаты доступны отдельно для сравнения; они не восстанавливают последовательность переходов.
- **Список ключей:** вкладка «Список ключей» принимает ключи через запятую, по одному на строку либо в одноколоночной таблице Markdown. Запятые и переносы можно сочетать; пустые элементы пропускаются. Можно вставить `New grid`, строку выравнивания `| :--- |` и затем ячейки `| CARSDIS-6 |`. Первая ячейка считается ключом. Регистр нормализуется; повтор одного ключа создаёт одного кандидата. Одна кнопка «Загрузить список» запускает всю выборку.
- **Доска Jira:** `https://hq.tutu.ru/secure/RapidBoard.jspa?rapidView=1482&projectKey=HOTELS`. Используются постоянный фильтр, подфильтр и статусы колонок. Быстрые фильтры и дополнительные параметры ссылки не применяются. Настройки видимости проверяются по локальному профилю; при их изменении нужна повторная диагностика.
- **Эпик Jira:** `https://hq.tutu.ru/browse/HOTELS-13561`. Файл и доступ к доске для этого режима не требуются.

В исходной выборке остаются HF-эпики; DF, отклонённые и другие типы задач исключаются с объяснением. Это правило относится к корням: связанные DF и обычные задачи доступны при раскрытии. Неизвестный признак HF не считается подтверждённым исключением. Аудит показывает кандидатов, дубликаты, причины исключения и недоступности.

При прямом вводе неверные строки и отдельно недоступные Jira-задачи остаются видимыми в общей таблице со статусом «Ошибка», исходным текстом, номером строки и известной причиной. У таких строк нет числовых метрик и календарных полос; они не входят в число HF, медиану или максимум. Если все строки имеют неверный формат, отчёт сохраняется без обращения к Jira. Пустой ввод отклоняется до создания задания. Исправить ошибку формата можно новым вводом.

**Обновить** для Jira-набора заново читает источник, связи и историю. Автономный набор обновляется повторным импортом XLSX. Для файла и прямого списка сохраняются все исходные корректные кандидаты, включая ранее исключённых и недоступных. Исправленная доступность задачи меняет строку ошибки на обычный результат; ошибки формата сохраняются до нового ввода. Отчёт только об ошибках формата обновляется локально. Для доски заново определяется состав. Отдельный эпик обновляется по стабильному id, даже при смене ключа.

Во время загрузки прежний набор остаётся видимым с пояснением. Новый результат появляется после успешного сохранения. Ошибка не заменяет предыдущий набор. При запуске восстанавливается прежний момент среза, без обращения к Jira.

## Раскрытие связанных элементов

В «Календаре по истории» стрелка у эпика показывает непосредственных детей по `contains` / `is contained in` и стандартному Epic Link (раздел Jira «Задачи, составляющие бизнес задачу»). Оба источника объединяются без дублей. Изначально всё свёрнуто; вложенный эпик раскрывается отдельно. Обычные задачи — последний уровень, подзадачи не показываются. Сворачивание скрывает всю ветку.

Дочерняя строка показывает полный жизненный цикл от создания до окончательного закрытия либо общего среза. У неё нет числовых дней, TTM или impediment. Полоски сохраняют фактические названия статусов, даты и переоткрытия. Категория статуса определяет закрытие; при её отсутствии используются согласованные названия HF/DF и задач. Неизвестное закрытие или неполная история дают предупреждение без вымышленной полосы.

Отклонённые элементы скрыты, допустимые потомки отклонённого эпика показаны под ближайшим видимым родителем с пояснением. Общий ребёнок доступен в каждой своей ветке. Фильтры и статистика работают по исходным эпикам; календарная ось учитывает все пригодные связанные истории и не сдвигается при сворачивании.

Для автономного импорта в форме «Файл» выберите **«История из XLSX, без Jira»**. В книге нужны общий срез и дополнение версии 1: листы «Элементы», «Связи» и «История». [Формат книги](docs/legacy-xlsx.md) и [готовый вымышленный пример](docs/sdd/changes/LOCAL-20260924-02-linked-issue-status-bars/evidence/linked-issues-demo.xlsx). Старая книга продолжает открываться и сообщает, что сведения о связях не загружены. Для прежнего сохранённого Jira-набора связи появятся после «Обновить».

Реализация прошла автоматические проверки; живые ответы Jira и фактический просмотр в браузере пока не подтверждены. Подробности — в [протоколе изменения](docs/sdd/changes/LOCAL-20260924-02-linked-issue-status-bars/verification.md).

## Jira и локальный профиль

Рабочий адаптер проверяется для Jira Server **9.12.10** на `https://hq.tutu.ru`. Настройки хранятся в `.local-data/jira-profile.json`; профиль текущего рабочего каталога создан по разрешённой диагностике. Он не включён в Git. Проверенный тип эпика имеет id `6`, поле Flagged — `customfield_10000`, вариант Impediment — `10000`.

PAT читает только локальный сервер из Связки ключей **Code Jira Relations PAT**. **tutu-jira** используется только при отсутствии первой записи, а не при отказе доступа. PAT не передаётся браузеру и не сохраняется в кэше. Приложение выполняет только GET к фиксированному адресу Jira, не следует перенаправлениям с токеном. Открытие приложения само по себе не читает PAT; загрузку или обновление запускает пользователь.

На новой машине отсутствие проверенного профиля даёт понятную ошибку. Диагностические scripts по умолчанию показывают план без чтения Keychain и сети. `--execute` выполняет запросы: запускать его только после согласования указанного объёма доступа. Сам план разработки разрешением не является.

```sh
npm run verify:jira
npm run verify:jira-sample
npx tsx scripts/verify-jira-board.ts
npx tsx scripts/verify-jira-board-adapter.ts
npx tsx scripts/verify-jira-import.ts
```

Текущий статус живой проверки и ограничения: [IMPLEMENTATION-HF-STATUS.md](IMPLEMENTATION-HF-STATUS.md). Другие доски требуют собственного проверенного профиля постоянной видимости. Если правило скрытия завершённых меняется, профиль нужно проверить заново: публичная конфигурация этой Jira не отдаёт само правило, оно подтверждено пользователем.

## Время и достоверность

- Первоначальное **Открыто** видно на календаре вне TTM. Эпик до первого согласованного активного HF-этапа показывает «TTM ещё не начат» при доказанной истории; неизвестное начало обозначается отдельно.
- **Решили делать** до первого активного HF-этапа также отображается вне TTM по решению пользователя. После начала работы действует непрерывный TTM.
- TTM идёт от первого согласованного активного этапа до окончательного закрытия или общего момента среза `asOf`, зафиксированного в начале загрузки. Возвраты `↩О` и промежуточное закрытие внутри TTM учитываются.
- Impediment показан отдельно, не вычитается из TTM. Полнота его истории и истории статусов оценивается независимо.
- Порядок переходов, повторные входы и миллисекунды сохраняются. Узкий интервал получает выносную подпись без растяжения длительности. Даты показаны в Europe/Moscow.
- Неполная история не достраивается из агрегатов или текущего статуса. Утраченное начало не подставляется из даты создания. Неизвестное значение отображается прочерком.

Поиск, фильтр исполнителя, сортировка, три масштаба календаря и детали эпика доступны над таблицей. Пороги heatmap и карта этапов сохранены из согласованной версии; неизвестным этапам пороги не назначаются.

## Ограничения и хранение

CSV/XLSX: до 20 МБ, 20 000 строк, 500 колонок. Прямой список: до 1000 уникальных корректных ключей и до 16 КиБ всего JSON-запроса в UTF-8. Доска: до 10 000 кандидатов; в любом Jira-наборе — до 1000 подходящих HF-эпиков. Один активный импорт/refresh. Превышение этих пределов даёт ошибку. Граф связанных элементов имеет отдельные пределы: 10 000 узлов с корнями и 50 000 рёбер; при первом превышении его расширение прекращается с предупреждением о неполноте. Строки раскрытия показываются порциями по 200 с кнопкой «Показать ещё».

REST не даёт атомарного снимка всей Jira: приложение повторно проверяет состав доски, настройки и метаданные задач, но фиксирует наблюдения за интервал загрузки. Обновление ручное; фоновый опрос Jira отсутствует. Запрос ограничен 20 секундами и тремя попытками для временных ошибок; большой Retry-After сообщает допустимое время повторного запуска.

Адаптер Server читает `expand=changelog` и проверяет `startAt`, `total`, уникальность и непрерывность. Если Jira обрезала историю, она считается неполной; неподтверждённый Cloud API пагинации не используется. Проверка реальной длинной истории ещё нужна.

`.local-data/dataset.json` содержит нормализованные входы и результат, записывается атомарно с правами `0600`. Каталог исключён из Git. Повреждённый кэш не уничтожается. Старый v2 мигрирует с резервной копией `dataset.v2.backup.json`, без изменения прежних числовых результатов. Формат старого автономного XLSX описан в [документации совместимости](docs/legacy-xlsx.md).

## Проверки и API

```sh
npm test
npm run build
```

Разработка ведётся через TDD и BDD: сначала сценарий поведения и падающая проверка, затем реализация и регрессия. Тесты используют вымышленные данные и временные каталоги; новый полный путь формы проверяется через настоящий локальный HTTP-сервер с подменённой Jira. Живые диагностические запросы запускаются отдельно. Визуальный просмотр в браузере фиксируется отдельно от автоматических тестов.

| Локальный API | Назначение |
| --- | --- |
| `POST /api/import` | CSV/XLSX, `X-History-Source: jira` либо `file`, `X-File-Name`, binary body |
| `POST /api/keys/import` | JSON `{ "text": "CARSDIS-6\nBUSDIS-9" }`, до 16 КиБ |
| `POST /api/board/import` | JSON `{ "url": "…" }` |
| `POST /api/epic/import` | JSON `{ "url": "…" }` |
| `POST /api/refresh` | JSON `{ "datasetId": "…" }` |
| `GET /api/jobs/:id` | Прогресс, аудит, ошибки, результат |
| `GET /api/dataset` | Последний сохранённый набор |

Все POST требуют `X-Local-Request: 1`; сервер проверяет Host и Origin. Импорт возвращает `202 { id }`. `POST /api/import` с `X-History-Source: file` используется автономным выбором формы. Отсутствие заголовка также сохраняет совместимость автономного XLSX.

### Спринты и бреши

Новая загрузка Jira показывает закрытые и начавшиеся спринты на задачах, Delivery-эпиках и главном эпике. Работа считается по категории Jira «В работе» у текущих native Sub-task, а при доказанно пустом составе — у самой задачи. Текущий состав применяется ко всей истории и явно подписан. Подтверждённая работа покрывает целый спринт. Тёмная отметка вплотную под полосой статусов главного эпика означает, что ни одна дочерняя задача не была включена в закрытый спринт; включённая, но не работавшая задача исключает брешь. Бреши ограничены проверкой идей/валидацией, реализацией и оценкой результата. Неизвестность и предварительные результаты активных спринтов на цветную полосу не наносятся; детали спринтов и числовые метрики сохранены.

Старые наборы открываются без сетевого обогащения: для спринтов нужен ручной refresh. XLSX остаётся вне нового скоупа. Контрольный пример без сети: `npx tsx scripts/verify-sprint-demo.ts`, затем `http://127.0.0.1:4331`. [Контракт и границы](docs/sdd/specs/sprint-continuity.md), [проверки и открытая приёмка](docs/sdd/changes/archive/2026/LOCAL-20260929-01-sprint-continuity/verification.md).

На строках задач спринты с участием задачи показаны целиком. Остальные спринты без участия видны только целиком внутри периода открытой задачи; спринты до создания, после закрытия и пересекающие границу такого периода скрыты. При повторном открытии периоды оцениваются отдельно.
